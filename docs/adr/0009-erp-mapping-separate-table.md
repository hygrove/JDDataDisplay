# ERP 映射独立成表，缺失映射不写行

ERP 编码来自一张独立源表（`ResourceData/ERP编码表.xlsx`，有效 188 条 `sku → ERP 编码` 映射），它与库存宽表是两种东西：库存宽表的行是「日期 × 店铺 × SKU」的快照，ERP 映射是与快照无关的静态对照。把 ERP 编码回填进库存宽表的预留列，会把"这个 SKU 尚未登记"固化成 0，从此无法区分"未登记"与"编码真的是 0"，而且 ERP 表一更新就得重算整张宽表。

因此 ERP 映射独立成表，由每日批处理幂等摄入：

```sql
CREATE TABLE IF NOT EXISTS erp_map (
    sku       TEXT PRIMARY KEY,   -- 库存 SKU
    erp_code  TEXT NOT NULL       -- ERP 编码；无映射则该 SKU 无行
);
```

缺失映射**不写行**（而不是写一行 `erp_code = 0`）：行存在即"已登记"，行不存在即"未登记"，这是唯一能让两种状态长期可区分的存法。

**本表是源表的镜像**：源表里删掉的映射，库里也不留——留着就是让库里存着"已经不成立的旧事实"，而运营在源表里删掉一行，本意就是"这个 SKU 不再登记"。因此摄入时除了 upsert，还会删掉源表里已不存在的那些行。

这条删除语义配一道**断崖护栏**：源表解析出的有效映射少于库里现有条数的一半时，只增不删（多半是源表被改坏了或写错了，此时删光已有映射比留着旧映射危险得多）。同理，源表缺失或解析不出任何有效映射时，一律不动库。

## Considered Options

- **回填库存宽表的 ERP 预留列**：查询时少一次 join，代价是把未知固化成 0（不可逆的信息丢失），且 ERP 表更新要重算宽表。
- **每次请求直接读 Excel**：实现最省事，但把源文件读盘放进请求路径，且违背本仓库"源数据进 SQLite、查询只读库"的既有约定。
- **独立映射表 + 批处理幂等摄入（选定）**：查询只读库；ERP 表当天变更经每日批处理生效；"未登记"与"编码为 0"在库层面就能分辨。

## Consequences

ERP 映射多一张表、多一次批处理摄入步骤。要注意两处口径差异是**有意**的：页面上没有映射时显示 `--`（让人知道该去登记），导出里写 `0`（下游模板要一个占位值）。不要为了让两者"一致"而把库里的缺失也写成 0——那正是本决策要避免的事。页面占位符用 `--` 而不是全站其它列的 `—`，也是有意：ERP 未登记是一个**业务状态**（该去登记），不是一个缺失数据，两者不该长得一样。

导出侧"写 0"待补货导出搬到后端时落地（见 `docs/adr/0008-restock-export-server-side-with-thumbnail.md` 与 `.scratch/inventory-restock-views/issues/05-server-side-export-with-thumbnail.md`）；在那之前导出表里还没有 ERP 列。

不要把 ERP 编码回填进库存宽表（那列保持空值预留）。也不要为了"补全"而给未映射的 SKU 造一个假编码：假编码会被下游当真值用——解析层因此自带两道自检：**ERP 编码等于 SKU**（列角色识别走偏的产物）与 **SKU 不是数字串**（库存 SKU 是数字串，非数字出现在 SKU 位说明列角色反了），命中即丢弃该行，不写进库。
