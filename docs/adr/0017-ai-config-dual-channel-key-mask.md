# AI 配置双通道存储，明文 key 永不回传前端

DeepSeek API Key 需要可配置（用户要求聊天面板里能直接改 key），而本服务经花生壳隧道**公网可达**（jdksh.top）且全站无登录（防滥用经用户拍板明确不做，见 `.scratch/ai-chat/spec.md` Out of Scope）。这两个事实组合出一条安全底线：

- **存储双通道**：环境变量 `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL` 为初始默认；UI 保存后写入 `backend/app/data/ai_config.json`（该目录已被 .gitignore 覆盖，不进公开仓库），**文件优先于环境变量**。
- **明文 key 永不回传前端**：配置查询接口只返回掩码（形如 `tk-a1b2…c3d4`，纯虚构示例）与是否已配置。若 GET 返回完整 key，等于把 key 挂在公网任人取用——防滥用可以不做，这条不能松。

公网用户对配置接口的最坏影响是**覆盖** key（改成一个无效值导致功能失效，重新保存即恢复），**取不走** key。这是「用户便利（UI 改 key）」与「机密性」之间可长期维持的平衡点。

## Consequences

- 掩码规则：保留前 6 后 4 位，中间省略号；key 过短时进一步收缩明文段，宁可看不出也不能漏全量。
- `ai_config.json` 含明文 key，属运行时敏感产物：只能留在 DATA_DIR（gitignore 覆盖），**永远不要**挪去仓库内其它位置，也不要在日志里打印。
- 文件与环境变量并存时文件优先；删掉文件即回退环境变量——这条优先级让「UI 改坏了」永远有一键回退路径。
- 后续若重启防滥用（ADR 可被推翻），掩码底线**继续保留**：它与防滥用是两件事，掩码防的是机密性泄露，限流防的是额度消耗。
