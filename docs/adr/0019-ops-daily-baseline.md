# 店铺日常运营数据：基准指标原子表与可增删改查语义

**状态**：Accepted（2026-11-05）
**范围**：`ResourceData/店铺日常运营数据/` 的**月报 JSON** → `backend/app/data/app.db` 新增 `ops_*` 表。
**不碰**：`daily_detail`（单品长表）、`inventory_*`（库存快照）、现有前端视图与全局样式。
**2026-11-06 补记**：新增只读 HTTP 接口需动 `main.py` 一行 `include_router`（见文末补记节），这是本 ADR 范围的显式扩展。

## 背景与动机

用户给出两份 2026-10 月报（自营 / POP，25 个字段，三层嵌套：月份 → 店铺 → 日期 → 指标），要求：

1. 去掉 5 个可计算指标：`转化率 / 客单价 / PPC / ROI / 佣金比例`；
2. 8、9、10 月一起入库；
3. 写入现有 `app.db` 的**独立新表**，不动单品表与库存表；日更格式稍后再说；
4. 4 个字段改名，改后的指标作为**基准指标**写入数据库：

| 源字段 | 基准指标名 | 落库列名 |
|---|---|---|
| 成交额 | 推广成交金额 | `promo_order_amount` |
| 成交金额 | JD联盟成交金额 | `jd_union_order_amount` |
| 佣金 | JD联盟佣金 | `jd_union_commission` |
| 佣金比例 | JD联盟佣金比例 | 派生指标，**不落库** |

5. 新表**不是只增不减**，需要增删改查。

实测证据（全量解析 6 个月报文件，1564 行）：

- 5 个派生指标确实可由原子列重算：8/9 月共 767/889/686/639/434 个可比样本，与源真值误差 <2% 的比例 **100%**。
- **`JD联盟佣金比例` 的分母是 `JD联盟成交金额`，不是销售额**：`佣金/成交金额` 在 8 月 POP 127 行、9 月自营 88 行上 100% 吻合（误差 <1%）；换成销售额，相对误差中位数变成 **11 倍 / 14.7 倍**。
- **10 月派生列大面积塌成「假零」**：10 月 POP 341 行中 PPC/ROI/佣金比例全为 `0.00`，转化率/客单价仅 1 行有真值；10 月自营 186 行中仅「慧采自营」31 行有真值。合计识别出 **1585** 个「源值为 0 但原子列可算」的格子。所以「删列」必须配「查询层重算」，否则看板会把 10 月显示成零转化。
- `/` 是「没抓到」，`0` 是「真实为零」：10 月自营访客数 62 行 `/`，POP 13 行整块缺字段。混同会把缺失伪装成没生意。
- 粒度冲突：`daily_detail` 是 `(date, shop, spu)` 商品级、950 行、仅 3 个 POP 店；运营数据是 `(date, shop)` 店铺级、17 个店。
- 目录里还有 `2026-11-04…json`：完全不同的日更 schema（顶层「日期+店铺名」、字段为「推广总点击数」等、每店字段数 2~10），本次不纳入。

## 决策

### 1. 事实表只存 19 个原子列，派生指标查询时重算

`ops_shop_daily` 的键为 `(date, shop, shop_type)`，`shop_type ∈ {self, pop}`。19 个 REAL 列全部允许 NULL。
5 个派生指标不建列，由 `derived_rows()` 用 **SUM(分子)/SUM(分母)** 重算——与项目 `transforms.compute_metrics` 的「先求和再相除」同一口径（把每日比率取平均会得到错误区间值）。

派生口径（`ops_metric_dict.formula` 是 SSOT）：

| 基准指标名 | 公式 |
|---|---|
| 转化率 | 成交人数 / 访客数 |
| 客单价 | 销售额 / 成交人数 |
| PPC | 花费 / 点击量 |
| ROI | 推广成交金额 / 花费 |
| JD联盟佣金比例 | JD联盟佣金 / JD联盟成交金额 |

分母为 0 或全 NULL ⇒ 返回 NULL，绝不返回 0。

### 2. 「基准指标写入数据库」= 指标字典，不是派生值列

新增 `ops_metric_dict`：24 行（19 原子 + 5 派生），每行含 `metric_key / cn_name / source_name / kind / db_column / formula / unit / is_baseline / sort_order`。
改名后的 4 个中文名是**唯一业务叫法**，源字段名只留在 `source_name` 供追溯。派生项的 `db_column` 为空串——名字与公式入库，值不入库。这样既满足「改名后的指标作为基准指标写入数据库」，又不违背决策 1。

### 3. 表语义：可增删改查，与长表铁律隔离

`ops_shop_daily` **不适用** `daily_detail` 的「只增不减」（ai-rules §1.1 / §1.5）：允许 UPDATE / DELETE。为让「人工修订」与「ETL 幂等」共存：

- `is_manual=1` 的行（人工新增或修改）**不被导入覆盖**；
- `ops_row_tombstone` 记录被删除的 key，导入时跳过，避免删掉的行下次跑批「复活」；`restore` 撤销墓碑后重新导入即可补回；
- UPSERT 用 `IS NOT` 做 NULL 安全的变化检测：**值没变就完全不写**，连 `updated_at` 都不刷新（否则二次导入会留下「全表被改过」的假象，验证脚本首次运行即抓到此问题）；
- `ops_ingest_log` 只记来源哈希与行数，**不做跳过门控**——本表允许人工改动，哈希一致不代表库里状态仍等于源文件。

### 4. 清洗约定

- `date` = 文件名年份 + 日期键月日，统一 `YYYY-MM-DD`；源里的「日期」文本列（无年份、零填充不一致）不采信；
- 顶层键必须等于 `YYYY-MM店铺日常运营数据`，日期键月份必须与文件名一致，25 个字段必须齐备——不符即 `ValueError`，不静默吞；
- `/`、空串、`-` → SQL NULL；`0` / `0.00` → 0.0；百分号 → 小数。

### 5. 隔离与不可逆动作

模块只创建 / 写入 `ops_*` 表。导入事务前后对 `daily_detail / inventory_daily / inventory_city_slow / inventory_processed_file / erp_map / alert_thresholds` 逐表取全行 sha256 指纹，**不一致即回滚**。生产导入另按 ai-rules §6：前置指纹落盘 → 备份 `app.db` → 执行 → 后置逐表核对。

## 后果与风险

- 新增 4 张表、2 个模块文件、1 份验证脚本；`config.py` 加 `OPS_DAILY_SOURCE_DIR`（可用 `JD_OPS_DAILY_DIR` 覆盖）。零新依赖。
- `app.db` 与业务数据一样不入仓（`.gitignore` 已有 `*.db` / `backend/app/data/`）。
- 月报文件若新增列，解析器会因「字段集合不符」报错——这是刻意的防漂移闸门，需同步 `ATOMIC_METRICS` 与字典。
- **未做**：日更格式适配（**2026-11-06 用户明确「保留不做」**）、前端页面。日更文件需另写适配器映射到同一原子 schema；HTTP 接口已列入文末补记节，动 `main.py` 时注意工作区可能有其他会话在途改动，且托盘服务不热重载。
- 「退款时长」「体验分」等单位源表未声明，字典 `unit` 留空，不臆测。

### 2. 新增两个只读接口

| 接口 | 响应 | 说明 |
|---|---|---|
| `GET /api/ops-daily/meta` | `OpsMetricMeta` | 下发 `ops_metric_dict` 24 项（key / label / unit / kind / formula / 精度 / sort_order）+ 数据截至日期；前端 0 硬编码列数与公式 |

- **响应格式**：沿用 `api.py` 现有端点的 `response_model=` 直接返回 Pydantic 模型，⛔ 不引入 `{code,message,data}` 统一包装（不写 `response_model` 会导致 `/docs` 响应体空白）。
- **挂载**：`main.py` 增加一行 `app.include_router(ops_daily_router)`，必须写在 SPA 回退路由 `/{full_path:path}` **之前**（与 `api_router` / `inventory_router` / `chat_router` 并列）；改前先 `git status` 确认无其他会话在途改动。

- **分页 / 导出**：表格复用项目既有 `PagedRows` 服务端分页契约（复用非新增）；导出走独立请求取筛选**全量行**，CSV 带 UTF-8 BOM。虚拟滚动不进 V1.0。
- **NULL / 0 / `--`**：真实 0 返回 0；NULL、分母为 0、全 NULL 返回 None 由前端渲染 `--`；禁 NaN / 0 伪装缺失。
- **派生粒度**：KPI 卡是筛选范围整体、矩阵行是单行，同源不同粒度，验收禁止互相比对。

### 3. 涨跌配色适用边界（D3）

用户拍板 **绿涨红跌**，与 `style.css` 现有 `--color-up:#1eb656` / `--color-down:#da2d2d` 完全一致 ⇒ **零改动全局令牌、零新增令牌**。

## 补记（2026-11-06 下午）：方案 C 月度趋势与月份间环比（SPEC v1.3）

**触发**：用户在静态预览后选定方案 C，并追加要求「月份之间可以标注增长或者下降的百分比吗」；同时确认表头不再标注「原子指标 / 派生指标」。按 SPEC §9 走变更登记 → **v1.3**，本 ADR 补记架构决策。A+B 主体、两个 GET、D1~D4、字典驱动、派生 `SUM/SUM` 与 NULL/0 口径全部不变。

### 1. 不新增端点，只扩展 `/data` 响应

- `OpsDailyData` 新增 `monthly: list[OpsMonthlyPoint]`；`OpsMonthlyPoint = {month, sales_amount, visitors, by_type}`。
- 后端 `_monthly_points()` 用一条 `GROUP BY substr(date,1,7)` + 一条按 `shop_type` 拆分的 SQL；**仍只有两个 GET**，不新增请求、不新增表、不跑 ETL、不写库。
- `by_type` 的键来自 `DISTINCT shop_type`，**不硬编码 self / pop**；每个月补齐全部键，缺的给 `None`，前端双折线不会因某月缺某类型而错位。
- **有意口径**：月度聚合**不随日期区间收窄**，返回全库全部月份；保留 `shop` 筛选、**忽略 `shop_type`**。日期不收窄的理由：页面默认近 30 天只落在 2026-10，若跟随 from/to 就只剩 1 个月份点 ⇒ 环比无从计算、首屏变空态；而把默认区间改成 90 天又会让 KPI 的等长上期落到无数据的 5~8 月，4 张卡环比全部退化成「暂无上期数据」。月度趋势看的是全库历史走势，本就不该被 30 天切片。类型不收窄的理由：方案 C 的价值就是「自营 vs POP」结构对比，选「自营」后 POP 线整条消失、图退化成方案 A。两点差异均在图表副标题显式标注。
- 只下发原子合计；**环比是派生值，由前端纯函数现算、不落库、不预聚合**，与本 ADR 决策 1 同源。

### 2. 性能诚实边界

`GROUP BY` 必须扫库内全部行 ⇒ 月度聚合的 SQL 扫描量随总行数线性增长，**不是完全与数据总量解耦**；但返回行数恒为月份数（当前 3 行、未来最多几十行），DOM 与响应体仍与总量无关。演进触发线登记在 SPEC §4.1：行数 > 10 万 或 `/data` P95 > 300ms ⇒ `month` 生成列 / 独立月度汇总表（另立工单）。当前 1564 行毫秒级，可接受，不提前预聚合。

### 3. 前端判定与渲染分离

- `frontend/src/modules/opsDaily.ts` 新增 `monthMom`（复用 `formatTrend` / `trendClass`，与 KPI 卡**同一套口径**）、`formatWan`、`spanMom`、`buildMonthlyChart`（SVG 几何）。
- 环比公式 `(本月 − 上月) / |上月|`；上期为 0 / NULL / 缺失 ⇒ `--` 且不染色；变化 < 0.05% 按持平。徽章位于**相邻两个月份线段的中点**下方，带 `<title>` 无障碍读数。
- 缺失月份 ⇒ 折线断开（⛔ 不用 0 伪装缺失）；不足 2 个月 ⇒ 图表区显示空态，不画假线。
- **手写 SVG，⛔ 不引入 ECharts / 图表库**；ops 页懒加载 chunk 只增约 3 kB，不进首屏包。
- 纵轴是非零起点放大区间（分类型值 min/max 各留 ≥12% 边距），副标题必须标注「非零起点」，否则 1% 的波动会被画成暴涨。

### 4. 表头单行化

`<thead>` 从 2 行（分组行 + 指标行）改为 1 行，删掉 `rowspan` / `colspan` 分组与「原子指标 / 派生指标（重算）」文字；派生列的区分只保留 `title` 悬停公式与列头颜色，不加文字标注或角标。勾选面板里的分组标题不是表头，保留。⚠️ 这覆盖 SPEC v1.2 §3 F-04 中「分组表头」的措辞。

### 5. 配色与验证增量

绿涨红跌沿用 `--color-up:#1eb656` / `--color-down:#da2d2d`（D3 边界见前一补记 §3）；徽章用白底 + 彩色描边 + 彩色粗字，**零新增 hex、零改动 `style.css`**。验证增量：后端断言 42 → **52**（新增 `[7.5]` 月度点的独立 SQL 校验、筛选 / 分页 / 空区间、10 张表指纹零变化）、前端断言 52 → **87**、`npm run build`、真浏览器实测。唯一事实来源：SPEC **v1.3 §4.2 / §10**。

## 补记（2026-11-06 17:19）：方案 1 落地、图例上移与徽章上移（SPEC v1.4）

**触发**：两轮静态预览后用户说「动手选方案1，改动：图中自营店徽章移到线条上方来，目前是在下方」。按 SPEC §9 走变更登记 → **v1.4**。A+B 主体、两个 GET、`monthly` 契约、环比公式与 4 个真实百分比、D1~D5、字典驱动、NULL/0、局部蓝与绿涨红跌全部不变；**后端 `ops_daily_api.py` / `ops_daily.py` 与 DB 全部 0 改动**。

### 1. 为什么删掉胶囊

v1.3 徽章是「白底 + 2px 彩色描边 + 全圆角」，白底与画布同色，只剩一圈粗描边孤立地浮在折线上，视觉上像可点击按钮 / 贴片，且会盖住一小段线。方案 1 直接**删除容器**：只留 `▲/▼ + 百分比` 彩色粗体字，用 `paint-order: stroke fill` + `var(--color-surface)` 描边保证压线可读。涨跌符号与颜色互为冗余编码（WCAG 1.4.1），色弱 / 黑白打印也能读；零遮挡、零新增色值。

### 2. 徽章统一上移到折线上方（D6）

`MONTHLY_CHART.badgeDy: +18 → -13`。原实现两条线的徽章都在线段中点下方；用户截图里自营徽章在下、数值标签在上，读起来像两组互不相关的数字。改为统一上移后两条线位置一致，徽章与折线的从属关系更直观。徽章 X 在**两月之间的线段中点**，数值标签 X 在**月份点**上，水平天然错开约 140px，同侧不会重叠（真浏览器截图已核对）。副产物：POP 线原本第二个徽章 y 会逼近 `bottom=170`，上移后也避开了下边界。

### 3. 图例是「读图前的元信息」，不是注释

把 `.od-legend` 从 `.od-chart-body` 末尾移到 `.od-chart-head` 之后、图表之前，做成独立「图例条」：浅蓝底 + 细边 +「图例」小标签 + 分隔线；线型样例用内联 SVG 从 `line.dash / line.hollow` 渲染，徽章样例取 `chart.lines[0..1].badges[0]` 的**真实首个环比**（⛔ 不造数，只有 1 个月时样例自动消失）。副标题删掉重复的「月份之间的徽章 = 环比（绿涨红跌）」，口径只留一处。
