# 归档判据用 key 覆盖，不用日期窗算术

源表目录里同一店铺的同类表存在大量时间窗重叠的文件，最省事的归档判据是"这份文件的日期区间已被别的文件盖住了"。但实测该判据会丢数据：卡求旗舰店的旧明细文件里有一条 2026-09-10 的数据行，在更新的文件中并不存在——行会从后续下载中消失，日期窗对此毫无察觉。因此归档改以 key 覆盖为准：**文件可归档，当且仅当它的每个数据 key 都在保留集的其他文件里出现**；日期窗退化为预筛，只用来减少需要读取 key 的文件数。

## Considered Options

- **日期窗算术**：区间相交即判冗余。直观、实现便宜，但会在"只存在于旧文件的行"上静默丢数据——已实证发生，不是假想风险。
- **内容级去重**：按整份文件的哈希或逐列比对。能识别真正一模一样的重复文件，但表达不了"两份文件各贡献一部分有效数据"这种常态，而后者恰恰是这个目录的常态。
- **按修改时间取最新 N 份**：看起来省事，但它把"新旧"等同于"覆盖能力"，一旦某份旧文件含有唯一数据行，这套逻辑会把它当成冗余扫掉。

## Consequences

预筛一旦漏判（把该读 key 的文件筛掉了），归档就会误删数据，因此预筛只允许**减少**读取量、不得决定归档与否。key 集合的读取与规范化必须复用批处理侧既有的规则（SPU 规范化、剔除合计行、日期归一），否则两边的 key 对不上，判据形同虚设。

判定取文件里的**全部** SPU，不受白名单过滤。看起来过滤后 key 更重合、归档更激进更省事，但白名单外的行今天不参与指标、明天就可能被重新登记进来；按过滤后的 key 判，等于把"当前不计入"当成"永远不存在"，那些店铺一旦复活，行就找不回归属了。宁可少归档，不可丢行。

这条判据在当前架构下不是保守，而是**必需**：长表 `daily_detail` 只增不减（`_upsert_long_table` 只有 `INSERT OR REPLACE`，无 DELETE），所以归档一个含独有 key 的文件并不会让那些行消失，而是把它们**永久冻结在库里**——源文件已经不在，数据永远不再更新，而且没有任何报错。日期窗算术制造的正是这种静默污染。
