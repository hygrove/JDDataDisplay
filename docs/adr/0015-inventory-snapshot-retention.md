# 库存快照只保留每店最新一份，旧快照永久删除

库存模块的数据源（`ResourceData/库存数据表/*.xlsx`）及其入库行（`inventory_daily` / `inventory_city_slow` / `inventory_processed_file`）按**每店最新一份**的保留策略滚动淘汰：某店当前最新快照之外的更早快照，连同源文件与入库行一并**永久删除**。删除是真删（`os.remove`），不进回收站、不归档、不留副本。

## 背景与动机

- **库存是时点状态，不是时序事件**。库存快照是「某店某日一次库存状态的完整导出」，它的全部下游消费（矩阵表、补货建议、预警、结构分布）都只用**单行快照内**的列：补货的「近30日出库」「30日有货天数」是**源表自带的列**（`inventory_metrics.CITY_SUFFIXES`），京东后台导出时已算好。因此删掉旧日期**不会**让任何一个业务数字算错——库存模块没有任何跨日期聚合。
- **旧快照没有管理价值**。库存管理决策只关心「现在库存怎么样」，历史某天的库存状态不参与任何补货/预警判断。
- **磁盘与查询成本真实存在**。实测生产目录 25 个 xlsx 覆盖 8 个快照日（家配单份 1.66MB、2000+ 列宽表）；`inventory_daily` 2796 行、`inventory_city_slow` 6339 行。ETL 每晚要全量解析这 25 份文件，而页面只用到其中 3 份。
- **快照不可回溯获取**。京东商家后台只能导出**当前时点**的库存明细，无法回溯下载历史某天的快照。这与 POP 销售明细（可按日期区间重新导出）性质根本不同。

## 与 ADR-0006（硬删不可逆 ⇒ 一律走回收站）的边界

ADR-0006 约束的是 `organize` 的**归档区清理**，前提是「归档文件是冗余的」——同一数据 key 在保留集里另有来源（ADR-0001 的 key 覆盖判定），删了能找回。库存快照不满足这个前提：它是该时点的**唯一来源**，商家后台导不出历史时点。

因此对库存快照，「送回收站」没有实际意义——回收站里的快照用户也不会去捞，而它反而制造「数据还在、只是搬走了」的错觉，掩盖了「这个时点已永久消失」的事实。库存快照走真删；**organize 的归档区仍走回收站**，两条链路互不影响（库存源目录 `ResourceData/库存数据表/` 也不在 `organize` 的管辖范围内——organize 只处理 `ResourceData/数据源表目录`）。

留下的只有**账，不是货**：删除清单记录文件名 / sha256 / 大小 / 删除时间，不含任何快照内容。

## 保留口径：每店最新一份，而非全局最新一天

保留集 K = 对每个店铺，取它在源目录中**可解析**的快照文件里最大的**表内「时间」日期**。

按全局单一日期（所有店共用一天）会导致：某店当天漏下载时，该店的全部历史被判定为「旧」而删除——而那些历史时点无法回溯获取，等于该店数据被清空。per-shop 口径下，落后店保留自己的上一份快照，其它店不受影响。正常情况下三店同日下载，K 收敛为单一日期，与「只保留最新一天」完全等价。

配套三条细则：

1. **日期以表内为准**，不取文件名里的 `2026-10-18`（文件名是约定，表内是真相）。
2. **损坏文件不删**：解析不出日期 / 无「时间」列 / 首行时间为空的文件，既不参与「最新」判定，也不删除，其入库行同样保留——无法证明其数据在别处有来源，就不许移走（同 ADR-0001 精神）。
3. **同 (shop, date) 多文件不删**：无法判定「哪一份才是最新」时，删除任何一份都可能丢数据 ⇒ 全部保留并在报告中点名。

## 删除顺序不可换

执行阶段固定三步：

```
④-1  删 inventory_processed_file 中对应哈希记录
④-2  删 inventory_daily / inventory_city_slow 中对应行
④-3  os.remove 删源文件
```

哈希记录是 ETL 的增量门控开关（文件哈希一致就跳过摄入），**先删它**等于关闭门控，于是任何中断点下次跑批都会重新摄入该文件、重建数据行，自动收敛回一致状态。

反序会出事：

- 先删文件后删行 ⇒ 中断后留下**僵尸行**：DB 里有行、源文件没了、哈希记录还在 ⇒ ETL 下次不重建 ⇒ 页面上出现查无出处的幽灵数据，**零报错**。
- 哈希记录最后删 ⇒ 中断后**静默丢数**：文件还在但因哈希一致被跳过 ⇒ 那天数据永久消失且无人报错。

## 前置门控

删除前必须校验新快照可信，否则整体不删：

- 每店在 K 中的行数 ≥ 该店上一份快照行数 × 60%（比例而非绝对值，家配 202 / 医拜 118 / 卡求 76 的量级差异不干扰）；
- 每店在 K 中至少解析出 1 行。

理由：`_parse_file` 对损坏文件**静默返回 None**（`inventory.py`），ETL 不报错。若新快照损坏而我们照删旧快照，库存页会直接空。**宁多留，不可删空。**

## Considered Options

- **按全局最新一天保留**：实现最简，但漏下载的店会被删空，且历史时点不可回溯 ⇒ 不可接受。
- **只删源文件、DB 保留历史行**：DB 不瘦身；且 ETL 的 glob 仍扫到全部文件 ⇒ 提速收益归零；页面日期下拉仍有旧选项，语义割裂。
- **只删 DB 行、源文件留档**：磁盘不释放；重建时 glob 会把旧文件全吃回来 ⇒ 保留集形同虚设。
- **走 organize 那套（归档 → 60 天 → 回收站）**：语义错配（organize 管冗余归档，库存是唯一来源），且不满足「永久删除」的明确要求。
- **只做一次性清理脚本、不改日常批处理**：每天仍会重新积累 ⇒ 治标不治本。
- **每店最新 + 源文件与三表同步淘汰 + 真删 + dry-run 优先（选定）**：口径精确（落后店不被删空）、删除顺序自愈、顺带让 ETL 稳态只解析 3 份文件、DB 可压回约 0.7MB。

## Consequences

- **`daily_detail` 不受影响**：POP 销售长表仍只增不减（`ai-rules §1.1`），与本决策无交集。`ai-rules` 新增 §1.5 明确「快照表 vs 长表」是两种表语义，防止后续把长表铁律误套到快照表上。
- **ETL 稳态提速**：删除旧源文件后，ETL 的 `glob("*.xlsx")` 自动只看到保留集 ⇒ 每晚从解析 25 份（其中多份 1.66MB 宽表）降到 3 份。删除动作本身就完成了提速，不需要重写 ETL。
- **DB 体积**：删行后 SQLite 空页不返还磁盘（实测 2.81MB → 删行后仍 2.81MB，`freelist_count` 531 页）；跑一次 `VACUUM` 后压到 **0.70MB**，耗时 15ms。VACUUM 需要临时空间并短暂持锁，放在批处理尾（非并发窗口）执行。
- **页面语义变化**：库存页不再提供跨店日期选择（数据里已无历史可选），改为**静态标注每店各自最新的数据日期**；落后店的日期会与其它店不同，页面必须让这件事可见，否则用户会以为看的是同一天的数据。
- **不可逆**：删掉的时点无法回溯获取。唯一的保障是 dry-run 清单人工过目 + 门控 + 自愈顺序 + 后置核对。
- **验证方式**：`backend/jobs/verify_inventory_retention.py`（独立脚本 + 自制断言计数器 + `sys.exit(1)`，⛔ 不引入 pytest）+ 后端真导入 + 现有库存接口测试不回归 + 前端 `npm run build` 与真浏览器实测。
