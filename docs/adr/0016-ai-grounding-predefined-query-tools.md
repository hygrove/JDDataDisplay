# AI 数据接地走预定义查询工具，不让模型写 SQL

AI 对话要「根据项目数据回答」。项目数据全在 SQLite（`daily_detail` 销售长表、`inventory_daily` 库存宽表等），表面上最灵活的路是 text-to-SQL：把表结构喂给模型，让它自己写查询。这条路被否了，因为**口径正确性是这个项目的命根子**：

- 比率类指标（转化率、ROI、均价）必须「先求和再相除」（ai-rules §2 SSOT），模型随手写的 `AVG` 就是错的；
- 明细与推广的过滤条件**有意不一致**（§1.3），这种隐性规则模型不可能知道；
- 库存宽表 182 列、城市码前缀、精确等值匹配衍生排除（§2 城市匹配）——schema 知识太重，错一列就是错一串数；
- 模型写 SQL 还要处理只读连接、注入面、超时——一堆为了灵活性引入的新风险，而且错得**静默**（AI 一本正经念错数，比报错危险得多）。

因此接地层是**一组预定义查询工具**（DeepSeek function calling）：每个工具是后端既有查询函数的只读包装（模块汇总、TOP 榜、明细分页、单品分析、库存 KPI、补货建议、预警汇总），模型只决定「调哪个、传什么参数」，**执行与口径都在项目代码里**。AI 说出的每个数字，都和页面上同一接口同源——这是把 §2 的 SSOT 纪律延伸到 AI 层。

## Considered Options

- **text-to-SQL**：灵活性无限；口径、安全、schema 知识三重风险，且错得静默。
- **预定义查询工具（选定）**：口径与页面同源、只读、可控；灵活性损失靠「工具粒度设计得够粗」补，将来不够用是**加一个工具**，不是换路线。
- **向量检索 RAG**：对结构化表格数据是过度设计（适合非结构化文档），还引入向量库与索引随每日刷新重建的耦合。

## Consequences

- 新增数据需求 = 新增一个工具包装函数，而不是放开 SQL。
- 模型能问的问题受工具集限制，这是**有意**的边界：宁可答「这个我查不了」，不要答一个错数。
- 查询工具复用现有聚合函数，意味着改聚合口径时 AI 与页面**自动同步**——不要为了「AI 专用」绕开聚合函数另写一份查询。
- `deepseek-reasoner` 与 function calling 的兼容性以实测为准；若不支持工具调用，reasoner 模式自动退化为纯对话（不带工具），并在界面上注明。
