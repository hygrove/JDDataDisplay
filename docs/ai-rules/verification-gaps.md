# 禁令 → 可自动化检查 映射表

> 本文件是 **`docs/ai-rules/README.md` 总纲「验证可信度缺口原则」的落地工具**：把手册里每条禁令，逐一标出"现在靠什么兜住、能不能变成跑得起来的检查"。
> 目标不是再加禁令，而是**把信任从人肉手册搬进系统检查**。每条禁令的理想轨迹：仅手册 → 可建 → 已自动化（然后从手册正文降级为引用）。
> 本表与 `README.md` 附录 B（脚本索引）互为表里：附录 B 答"有哪些检查可跑"，本表答"每条禁令被哪道检查兜住、还有哪些缺口"。
> 本表随代码演进维护；与代码不符以代码为准。

## 图例

- **覆盖状态**
  - `已覆盖`：已有自动化检查能抓此禁令的违反。
  - `部分覆盖`：有相关检查但不完整，或只覆盖部分失败形态。
  - `仅手册`：只有文字禁令，无自动化检查（靠人记 / AI 记）。
- **自动化潜力**
  - `已自动化`：检查已存在，只需保证跑得到（pre-commit / CI）。
  - `可建`：目前仅手册，但技术上能做成一道检查。
  - `难自动化`：是写码/设计/流程纪律，不构成可机检的"违反"。
  - `不适用`：非检查类约定。

## 优先级建议（ROI 最高的"可建"项）

按"失败后果严重度 × 实现成本"排序，**优先做这 5 道**——它们都针对"静默数据损坏"或"业务数据意外公开"这类不可逆风险，且实现便宜：

1. **静态扫描 `DELETE FROM daily_detail`**（§1.1）——一行 grep 级检查，守住最致命的静默损坏。
2. **pre-push hook**（§6.1）——把现有 grep 命令串成一道闸门，防 public 仓泄漏业务数据。
3. **`requirements.txt` 不含 pytest**（§3）——守住 freeze 复现前提。
4. **路由 `response_model` 扫描**（§3）——防 `/docs` 响应体空白这类低级遗漏。
5. **`JD_ORGANIZE` env 检查**（§4）——防开关误置导致 organize 在生产误执行。

> 这 5 道做成后，手册 §1.1 / §3（pytest、response_model）/ §4（开关）/ §6.1 就能从"仅手册"降级为"引用检查"，正是总纲说的"优先修检查、再删禁令"。
