# 架构方案与注意事项手册

> 把一套"电商/业务数据可视化"类项目的**可复用架构与技术方案**萃取成手册。做相似项目时，照"功能 → 用什么技术/架构 → 为什么 → 避坑"走，少踩已经踩过的坑。
>
> **用法**：正文按八大类组织——**前端 / 后端 / 数据库 / 测试 / 运维部署 / 跨端契约 / 工程治理 / 其他**。标 🔴 的是"踩错会静默损坏数据或让人误以为改好了"的致命项，迁移时优先照搬；标 ⭐ 的是高杠杆、强烈建议直接抄的好方案。文末附"相似项目迁移速查"。
>
> 技术名词（FastAPI / Vue3 / SQLite / Polars / Pydantic 等）仅为示例，可按栈替换。

---

## 背景与心智模型

一类典型场景：每天把散落的 Excel/CSV/接口数据，批处理成结构化数据，由一个**单端口后端同时提供「数据接口 + 前端页面 + 图片」**，浏览器里的 SPA 把数据画成表格、指标卡和趋势图。

核心链路：

```
数据源(Excel/CSV/API/DB) ──批处理(ETL)──▶ 轻量数据库 + 缩略图 ──单端口后端──▶ 浏览器 SPA 渲染
                                                  ▲                         │
                                                  └──── 前端只调统一数据接口 ────┘
```

**关键认知**：让数据库直接作为 API 的数据源，**不要**在"数据库"和"接口/前端"之间再落一层中间 JSON 文件——中间产物会和你产生双真相、易漂移。前端始终只调统一数据接口，底层是 Excel 还是数据库对它透明。

通用技术栈参考（仅为示例，可按栈替换）：

| 层    | 推荐选型                                   | 一句话职责                 |
| ---- | -------------------------------------- | --------------------- |
| 数据生产 | Python + Polars/DuckDB + 校验型 schema 库  | 清洗/聚合/建模校验            |
| 存储   | 嵌入式单文件数据库（如 SQLite，不进版本库）              | 轻量、随项目走、零服务           |
| 服务   | 单端口 Web 框架（如 FastAPI/Express）+ 应用服务器   | 同时托管 API + SPA + 图片   |
| 展示   | 现代前端框架（如 Vue3/React）+ 构建工具 + 状态库 + 图表库 | SPA、状态、路由、图表          |
| 调度   | 操作系统计划任务 / CI                          | 无人值守跑批                |
| 产物   | 运行时数据目录（git 忽略）                        | 数据库 / 图片 / 缩略图，每次跑批重建 |

## 一、前端

### 1.1 Design Tokens + 字号缩放系数 

- **功能**：全站样式统一、可读性可调、避免魔法值。
- **技术/架构**：用一个全局样式表的 `:root` 作**设计变量单一事实来源**——文字色阶/背景/边框/品牌色/功能色/圆角全是 CSS 变量；全局字号靠一个缩放系数变量，所有字号写成 `calc(基准px * 系数)`，改一个变量即全站缩放。运行时把系数写入 CSS 变量 + 本地存储持久化，首屏在框架挂载前读回防闪烁。
- **为什么·好处**：消灭散落的魔法值与样式碎片化；字号多档满足高分屏/小屏可读性。
- **避坑&#x20;**：
  - 图表库（SVG/Canvas）内的标签字号**不参与 CSS 变量缩放**（坐标写死会重叠）——专门写校验脚本防这条回退。
  - 禁止手写比最浅文字令牌更浅的灰；文字令牌**不得用于边框/分隔线**（加深后虚线过重）→ 用专用分隔线令牌。
  - 自动化闸门：字号令牌校验（强制所有字号走变量）+ 可读性校验（对比度下限 + 阶梯单调 + 禁手写浅灰 + 禁文字令牌当边框），并入构建/推送前闸门。

### 1.2 用稳定 `data-testid` 当沟通契约

- **功能**：AI/协作时精准描述"改哪个元素"。
- **技术/架构**：维护一份"路由→页面→组件→关键元素"登记表，每个元素一个稳定 `data-testid`。描述改动只要说 testid，协作方/AI 能唯一定位，不再靠"上面那个搜索框"猜。
- **为什么·好处**：前端复杂后用"中文文案/截图"描述元素常失真、改错位置；沟通零歧义、零侵入（只多一个属性）。
- **避坑**：新增"对用户有意义/以后可能要改"的区块时顺手加 testid 并回写登记表；列表项用同一 testid 命名整类，定位单个用索引。

### 1.3 判定与渲染分离（纯函数 + 单测）⭐

- **功能**：业务判定（口径/阈值/格式化/占位符）要可测试、不错位。
- **技术/架构**：判定逻辑集中在纯函数模块（不碰网络、不碰 DOM），视图层只渲染。例：可售天数文本（0 是有效值不能当缺值）、缺口标记文案（与导出文件逐字同口径）。
- **为什么·好处**：`空值被当 0 排序`、`阈值内小额变动误染`这类错页面上看正常，只有单测能抓；纯函数可直接用 node/单测断言，多视图共用同一份实现，避免口径漂移。
- **避坑**：判定用的格式化函数**自己写**，别复用通用 formatter（空值可能要显示 `--` 而非 `0.00`）；服务端判定与前端展示文案用**同名同义常量**，两边各一条断言锁住防漂移。

### 1.4 状态管理分层（业务/瞬时UI/偏好）

- **功能**：状态不互相污染、易于推理。
- **技术/架构**：刻意把状态拆成"业务数据"（清单/汇总/行/筛选态）、"瞬时 UI"（仅路由级加载遮罩）、"用户偏好"（勾选了哪些指标，按模块存本地存储）三类。
- **为什么·好处**：三者语义不同，混在一起会互相污染；偏好 store 过滤已下线的指标键，旧存档不报错。
- **避坑**：记忆口诀——业务数据进业务 store，瞬时 UI 进 UI store，用户偏好进偏好 store + 本地存储。

### 1.5 应用装配顺序铁律（状态库先于路由）

- **功能**：路由守卫要点亮加载态。
- **技术/架构**：框架装配顺序必须是"状态库 → 路由 → 挂载"；状态库必须在路由之前。
- **为什么·好处**：路由守卫里会调用状态库点亮遮罩，依赖已装配的状态库；否则首次导航报"没有活跃的状态库实例"。
- **避坑**：状态库调用必须在导航**运行时**进行，不能放模块顶层；错误兜底复位防遮罩永久卡死。

### 1.6 配置驱动（新增模块不写新页面）

- **功能**：多模块同质页面，避免重复造页。
- **技术/架构**：用"模块注册表 + 指标清单"共同驱动表格列/指标卡/趋势图。新增模块 = 后端加一条模块规格 + 前端加一份配置，**不写重复页面**。
- **为什么·好处**：模块页是通用骨架，重复造页面 = 重复 bug；加模块基本零新页面，路由/表格/图表/虚拟滚动全部复用。
- **避坑**：指标超出当前集合时，后端加字段 → 前端类型同步 → 指标配置加规格并引用。

### 1.7 不整模块推给前端（分页 + 虚拟滚动）

- **功能**：单模块可能近十万行，全推前端会卡死。
- **技术/架构**：列表接口强制分页，滚动到底自动拉下一页；图表只用聚合结果（几百~几千点查询时现算），不画原始点。
- **为什么·好处**：首屏快、内存可控；离页重置状态，后端无缓存直查。
- **避坑**：Web Worker（超大 JSON 解析放后台）当前数据量用不到，**预留位置**别过早引入；单模块接近十万行且前端重过滤时再加。

### 1.8 图表库读不到 CSS 变量（用取色工具）

- **功能**：图表配色要跟设计令牌走。
- **技术/架构**：CSS 变量只生效于 CSS 属性，写进 SVG/Canvas 的填充色会静默失效；用"从根节点读真实色值 + 加透明度"的工具函数替图表库取色。
- **为什么·好处**：图表配色仍跟令牌走，改令牌图表同步变。
- **避坑**：SVG 三坑——散点包围盒取退化值改用标准包围盒；只靠描边认标记线会误计，还要匹配单段直线；标记线标签横竖必打架 → 阈值数字放图下说明行。

### 1.9 涨跌配色：先问"涨的是钱还是盈亏"

- **功能**：涨跌/盈亏配色别误导。
- **技术/架构**：成交用红涨绿跌（国内习惯）；"加投/减投"无盈亏语义用中性色；"操作成功"的绿与"数值上涨"的绿刻意区分。
- **为什么·好处**：国内用户默认红涨绿跌；但"成功反馈绿"与"数值上涨绿"语义不同，混用误导。
- **避坑**：改动前该色若散落多处硬编码，收进令牌；新增涨跌展示一律走涨跌令牌。

### 1.10 布局坑：flex `min-width:0` 与列宽用类名

- **功能**：Flex 布局稳定。
- **技术/架构**：flex 子项必须显式 `min-width:0`（默认 `auto=min-content` 撑开定宽列）；列宽用显式类名，**不用 `:nth-child`**（依赖"每行列数相同"隐藏前提）。
- **为什么·好处**：`min-width:auto` 让长内容撑破布局；`nth-child` 在列数变动时静默错位。
- **避坑**：跨浏览器布局炸弹——「定高容器 + 底部对齐 + 内容高度自适应」三者同现（不同浏览器不一致）→ 修法：容器不定高 + 顶部对齐 + 显式行高；无头环境下差异常不复现，改中间量排查。

### 1.11 资源优化：缩略图多尺寸（避免下 MB 原图）

- **功能**：列表里每格只显示百来像素，下原图浪费带宽。
- **技术/架构**：批处理生成多尺寸缩略图（多种现代格式）；前端按展示框实际尺寸引用对应目录，避免为小框去下 MB 级原图。
- **为什么·好处**：列表流畅；多格式 + `srcset` 让浏览器自选。

## 二、后端

### 2.1 单端口后端托管一切（API + 页面 + 图片）

- **功能**：小流量内部看板不想维护反向代理 + 独立前端服务器。
- **技术/架构**：一个后端进程、一个端口同时提供业务接口、构建后的前端静态资源、原图、缩略图；其余路径回退到 SPA 入口页。
- **为什么·好处**：运维只管一个进程；前后端同源，无跨域无代理配置。反向代理（gzip/缓存/HTTPS）仍是可选增强，不是门槛。
- **避坑 🔴**：**挂载顺序铁律**——静态资源（图片/缩略图/前端 assets）的挂载**必须写在 SPA 回退路由之前**，否则图片请求会被回退成入口页（表现为"页面能开、图片全 404"）。

### 2.2 数据源协议解耦（配置驱动加数据源）

- **功能**：接入新数据源不应触动聚合/展示链路。
- **技术/架构**：定义统一的"数据源"接口/协议——任何数据源只需实现"名字 + 取数()→标准长表"。写方（Excel 源）、读方（数据库源）、将来的外部库源都实现它，ETL 主流程完全不用改。
- **为什么·好处**：读写分离让接入新源 = 写一个取数函数；下游无感。将来从嵌入式库切到服务式库时零改动下游。
- **避坑**：把"读"和"写"分开实现，别混在一个类里，避免切换底层时撞名、语义不清。

### 2.3 API 缓存 + 可重入锁 + refresh 必须清缓存

- **功能**：聚合/扁平化是性能关键，切区间/切单品应毫秒级。
- **技术/架构**：用模块级缓存 + 可重入锁（因聚合内部会再调取数，普通锁会死锁）做双重检查加锁懒加载；跑批刷新接口同步跑批后**必须清空缓存**。
- **为什么·好处**：无缓存时重算只在刷新时触发；真正的重活被摊薄到首次访问。
- **避坑**：改完后端**必须真导入/真启动验证**（语法检查只查语法查不出引用错误）；刷新后接口仍返回旧数据，第一反应是缓存没清或旧进程还在跑（后台服务不热重载）。

### 2.4 后端直查数据库，无中间 JSON

- **功能**：API 提供数据，不要多一层产物。
- **技术/架构**：API 每次请求直接查询事实表，摄入落库即生效，无中间 JSON 文件、无多余内存缓存（轻量场景下）。
- **为什么·好处**：单一数据源，规避"数据库与 JSON 双真相"；刷新延迟低。聚合时保证行序确定（某些引擎默认行序随线程漂移，会导致图表重排）。
- **避坑**：所有分组/去重都带"保持顺序"参数——别当冗余参数删掉，否则两次刷新图表会重排。

## 三、数据库

### 3.1 嵌入式单文件数据库（而非起服务的 Postgres/MySQL）

- **功能**：项目要"轻量、能随仓库走、能异地克隆复现"。
- **技术/架构**：用嵌入式单文件数据库（如 SQLite），数据库文件既是库又是普通文件，不进版本库。
- **为什么·好处**：不需要多连接/账号权限体系，零新依赖零运维；克隆后跑一次批处理即恢复。若将来要接外部数据库，可预先留一个"读写数据源"抽象层，下游零改动。
- **避坑**：数据库是"跑出来的产物"，**不要进版本库**（忽略配置双保险）；异地克隆先铺样例数据再跑批。

### 3.2 长表只存可累加原始列，比率指标不入库

- **功能**：要做"按天/按店铺/按区间"多层汇总的指标看板。
- **技术/架构**：事实表只存可累加的原始计数（访客/成交/金额/推广/退款…）；转化率、客单价、ROI、占比等比率**全部在查询时"先按维度求和、再相除"派生**，分母为 0 或缺失时返回空（前端显示占位符）。
- **为什么·好处**：比率直接入库，跨期/跨店/跨区间汇总时把它们相加或平均会得错误结果（例：两天各 10%、20%，区间真实是 15%，简单平均只是巧合对）。不入库则单日/店铺/区间多层口径永远一致。
- **避坑**：任何"把比率也存进去"的冲动都要压住——这是统计正确性的命根子；比率口径（求和 vs 比值）在前端指标配置里也要显式声明。

### 3.3 增量摄入 + 内容哈希门控

- **功能**：数据源每天增长，全量重洗慢且没必要。
- **技术/架构**：用一个"已处理文件清单"表记录每个源文件的相对路径 + 内容 sha256；本轮哈希与上次相同且库非空 → 跳过整段摄入；任一文件变了 → 重算整张干净事实表并幂等 upsert，再刷新哈希。
- **为什么·好处**：未变源零重算；同一份数据反复跑结果一致（唯一键 + 幂等写入）。用"一点正确性换复杂度"——文件级门控已能在"没变就跳过"上拿到增量收益，剩余情况用幂等 upsert 保正确。
- **避坑**：门控比对的是**全量内容哈希**，不含修改时间/大小——增/删/改名/改内容一律整表重算，避免"文件动了但哈希没变"的漏更。若数据源是数据库/接口，把这个门控换成"上游游标/水位"机制。

### 3.4 事实表只增不减（防僵尸行）🔴

- **功能**：支持"把某个源表移走/归档"而不损坏历史聚合。
- **技术/架构**：事实表全程只有幂等写入（upsert），无删除。
- **为什么·好处**：把源表"移走"不会清理对应行，会冻结成**僵尸行**——仍在聚合、永不更新、零报错，是最危险的静默损坏；只增不减则数据只会被新摄入覆盖、不会被误删。
- **避坑 🔴**：凡涉及"把源表移走/归档"的功能，必须证明被移走的每个键在别处有来源（整理器的"键覆盖"判据正是为此）。这条是头号致命项。

## 四、测试

### 4.1 校验脚本闸门（把约束变成自动报错）

- **功能**："靠人记约束"会忘。
- **技术/架构**：一系列校验脚本 + 总闸门：字号令牌校验、可读性/WCAG 校验、纯逻辑单测、前后端聚合口径一致性校验、展示判定单测。后端用标准库单测（不引额外框架，为异地复现 freeze）自写断言。
- **为什么·好处**：写成断言，CI/本地立刻抓回退；设计令牌、聚合口径等被脚本锁死，不因一次手滑退化。

### 4.2 真浏览器实测（不能只 grep 构建产物）

- **功能**：交付前验证浏览器真的生效。
- **技术/架构**：交付前必须真实浏览器实测（而非自带的无头浏览器），用稳定 testid 区分表头/数据行；"看起来没变化"先强刷排除缓存。
- **为什么·好处**：只看构建产物只证明构建通过，不证明浏览器生效；抓到"构建过但页面没动""图片 404"等只有真浏览器才暴露的问题。

## 五、运维部署

### 5.1 两套部署形态（dev 代理 / prod 同源）

- **功能**：开发与生产共用同一后端。
- **技术/架构**：开发用前端 dev server 通过代理把数据/图片请求转发到后端本地地址；生产构建后由同进程同源托管。
- **为什么·好处**：无需两套后端；改前端只需构建（后端实时读产物）无需重启。
- **避坑&#x20;**：
  - 代理目标必须写 IP（如 `127.0.0.1`）而非主机名（新版本 Node 把 localhost 解析成 IPv6，后端只听 IPv4 → 整站 502，但命令行 curl 正常极具迷惑）。
  - 代理必须列全所有前缀（数据/图片/缩略图），漏一个会让某类资源在生产正常、开发全裂。
  - 前端可见变化先构建再**强刷**；入口 HTML 已禁用缓存。

### 5.2 SPA history 回退 + 入口 HTML 强制 no-store

- **功能**：用 history 模式路由（URL 无 `#`），直接访问深链不 404。
- **技术/架构**：前端路由 history 模式，直接访问深链靠后端回退返回入口 HTML；回退的入口 HTML 强制 no-store。
- **为什么·好处**：带哈希的资源是内容寻址可长缓存，但入口 HTML 是入口，缓存它会导致"改了前端却看不到变化"；刷新不 404，重新构建用户立即拿新入口。
- **避坑**：入口 HTML 之外真实存在的文件优先直接返回，避免把静态小文件也回退成 HTML。

### 5.3 调度跑「工作区代码」而非固定 commit 

- **功能**：无人值守跑批。
- **技术/架构**：每晚的调度任务跑的是**工作区里那份代码**，不是某个提交。若用 CI/容器部署，改成"跑特定 tag/镜像"。
- **避坑&#x20;**：未提交的半成品会被当晚任务直接吃到 → **半成品不过夜**，要么尽快提交要么当天别留。后端改动要生效要么重启服务，要么等下次新进程（新进程天然拿新代码）；后台服务不热重载。

### 5.4 不可逆文件搬移默认 dry-run 

- **功能**：首次归档/整理是规模最大的一次不可逆动作。
- **技术/架构**：整理功能默认 `dry-run`（只读出清单与报告，零搬动）；非法值回退 dry-run；显式开启才真搬；关闭整段跳过。首次上线三步走：dry-run → 人工过目 → 转自动（只改环境变量）。
- **为什么·好处**：默认什么都不搬 = 默认安全；回滚跨目录。
- **避坑&#x20;**：**整理只改文件位置、不改数据**（数据逐格不变是验收闸门）；归档不是删除、隔离不是排除；清单缺失 = 那批不可回滚，**别删**。

### 5.5 最小安全流程（前置指纹 → 断言 → 执行 → 后置哈希核对）

- **功能**：任何不可逆动作（归档/迁移/删数据）。
- **技术/架构**：四步：① 前置指纹落盘（源文件哈希 + 大小 + 目录清单）② 断言前置状态（防重复执行）③ 执行 ④ 后置逐份核对（内容哈希 + 清单集合 == 实际集合 + 环境未被污染）。
- **为什么·好处**："能撤回"要有前置基线才成立；恢复的唯一可信判据是逐字节比对，不靠"手工改回来"；事后可审计可回滚。

### 5.6 回收站而非硬删（降级不中断）

- **功能**：清理过期归档时别硬删。
- **技术/架构**：过期文件逐个送系统回收站（可还原）；回收站不可用时只在报告里标记延迟，**不硬删、不中断批处理**。
- **避坑**：回收站有容量上限，超出后系统会永久删除最旧条目（可能波及无关文件）——报告每次都带这句提醒。成功判据**不能只看返回码**（某些系统在成功送回收站时返回非 0 码），要看"原位已消失且回收站条目增加"。

### 5.7 公开仓库：业务数据禁入仓（忽略配置双保险）

- **功能**：仓库是 public 时别泄露业务数据。
- **技术/架构**：业务数据目录、数据库文件、运行时数据目录全部忽略；样例数据刻意脱敏入库。推送前扫描：忽略配置复核、密钥正则、外网硬编码、真实业务标识。
- **避坑&#x20;**：核验只能看远端主干，**不能用本地全量日志/分支**（`--all` 会把未推送分支与工作区一并算进来，极易误判"业务数据已入库"）。

### 5.8 推送前验证闸门（红灯不推）

- **功能**：把"改了不生效""数据泄露""可读性退化"挡在推送前。
- **技术/架构**：推送到 public 远端前必过：后端真导入/启动 + 后端单测 + 前端构建 + 可读性/令牌校验；串行执行（并行跑前端构建与后端导入会假报产物不存在——构建清空重写撞上后端读目录）。
- **好处**：把三类事故挡在推送前。

## 六、跨端契约

### 6.1 前后端类型对齐（schema ↔ 前端类型 手工或代码生成）

- **功能**：前后端数据结构要一致。
- **技术/架构**：后端用校验型 schema（如 Pydantic）作为数据结构事实来源；前端类型手工或代码生成对齐；前端另有"展示哪些指标"的配置作为展示事实来源。新增指标需同步三处（后端 schema / 装配 / 前端配置与类型）。
- **为什么·好处**：未引代码生成器时，手工对齐 + 前端类型检查构建兜底，零额外工具链；字段变更两处一起改，构建期就能抓类型漂移。字段多到手工痛苦时再引代码生成器。
- **避坑**：给行数据加字段必须**两处同时改**——装配处塞值 **且** 响应模型显式声明；若模型配置为"忽略未知字段"，未声明字段会被静默丢弃（白加 → 前端 undefined 但没人报错）。

### 6.2 单一事实来源（SSOT）分层

- **功能**：多处各写一份 = 口径漂移、改一处漏九处。
- **技术/架构**：指标定义、设计令牌、指标勾选配置各自是唯一事实来源，下游一律引用，不写魔法值。
- **为什么·好处**：改一处全局生效。
- **避坑**：组件样式一律引用令牌色，不写魔法色值。

## 七、工程治理

### 7.1 接手规则文档：AI/新人可读的"怎么改才安全"

- **功能**：让接手者（人或 AI）立刻知道致命禁止项。
- **技术/架构**：一份文档集中写"怎么改才安全""为什么不能这么动"，按"约束 → 为什么 → 怎么验证"组织，论据指向决策记录与工作记录。
- **为什么·好处**：AI 接手最易"看起来改好了其实没改/静默损坏数据"；把铁律钉成文档比靠记忆可靠，新人第一件事读它立刻知道致命项。

### 7.2 ADR：非显然技术选型先写决策记录

- **功能**：决策意图与演进理由要不丢失。
- **技术/架构**：为每个非显然决策写"为什么 + 边界 + 撤销代价"的决策记录（ADR）。要求"非显然选型先写 ADR 再动手"。
- **为什么·好处**：决策意图不记录，换人就会"凭记忆重写"或误删；决策可追溯可否决可撤销，一键恢复而非重写。
- **避坑**：**全局布局类方案（如设计令牌 + 字号缩放）补做时也要走 ADR 流程**——这类方案好在，但"为什么这么选 + 边界"若只散落注释，后来人易误改。

### 7.3 协作纪律（防代码层技术债）

- **功能**：代码可维护。


- **技术/架构**：中文注释 + 英文标识符；类/公开函数必写文档注释；复杂逻辑加"为什么"；⛔ 禁决策残留（方案 A/B 只用一个，清掉另一个痕迹）；产出默认单文件。
- **为什么·好处**：决策残留（"本来想用 B"的注释）让后人困惑并误恢复已弃方案；单文件产出降低衔接成本。

### 7.4 评估先行（接到需求先出五步评估）

- **功能**：避免"拿到需求就写"导致选型返工。
- **技术/架构**：接到功能/项目需求先出可行性、难度分级、主流方案 vs 用户方案差距、备选路线、演进趋势五步评估，再动手。

### 7.5 领域词汇表（防语义漂移）

- **功能**：同一词在不同语境含义不同会导致判定错误。
- **技术/架构**：定义领域术语及"避免用词"（如「归档≠删除」「隔离≠排除」「断档≠缺口」「键覆盖≠区间重叠」「未登记≠编码是 0」）。
- **为什么·好处**：跨模块/跨人沟通用词一致；AI 生成判定逻辑时不会踩语义坑。

## 八、其他（残余与诚实提醒）

- **撤销的功能别凭记忆重写**：功能若已撤销，重启用先找回原始 spec 与决策记录，**别凭记忆重写**。
- **整理/归档工具不是性能优化**：这类工具实测往往是净耗时（自己要先读全部文件算键），唯一价值是目录可读性，**别拿性能推销它**。
- **全局布局方案也要补 ADR**：设计令牌 + 字号缩放这类方案补做时容易漏掉决策记录——方案好在但"为什么这么选 + 边界"无集中记录（仅散落注释）。相似项目补这类全局布局方案时务必同步写一条 ADR。
- **选库要一致**：数据处理刻意用一种 DataFrame 库（如 Polars），迁移时注意别无意识混写另一种（如 pandas）风格代码。
- **Web Worker 别过早引入**：数据量未到阈值，预留位置即可，别 premature 优化。
