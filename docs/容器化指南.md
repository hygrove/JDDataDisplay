## 1. Docker 生态全景

一句话版本：**Docker = 把"应用 + 依赖 + 环境"打包成一个标准化集装箱，让它在哪里都跑得一模一样。**

| 概念 | 是什么 | 比喻 |
|---|---|---|
| **Dockerfile** | 描述"怎么造集装箱"的配方单 | 装修图纸 |
| **Image（镜像）** | 按配方造出来的只读模板，分层存储 | 盖好的酒店样板间 |
| **Container（容器）** | 镜像跑起来的实例，可启停可删除 | 开业营业的酒店 |
| **Registry（仓库）** | 存放/分发镜像（Docker Hub、Harbor） | 酒店连锁总部仓库 |
| **Volume（卷）** | 数据持久化，容器删了数据还在 | 酒店的地契（不随装修拆掉） |
| **Network（网络）** | 容器间通信的虚拟网络 | 酒店内部电话线 |
| **Compose** | 一个 YAML 定义/编排多个容器 | 一次规划整个度假村 |
| **K8s** | 大规模容器的调度/自愈/扩缩容 | 连锁集团总部 |

**容器 vs 虚拟机**：虚拟机是"每户一栋别墅，自带全套地基水电"（重、分钟级启动）；容器是"同一栋公寓楼里隔出的房间，共享地基（内核）、各自独立门牌"（轻、秒级启动）。

## 2. 容器技术四层架构（酒店连锁比喻）

从上到下，每层解决一个痛点：

| 层级 | 代表角色 | 比喻 | 干什么 / 解决什么痛点 |
|---|---|---|---|
| **层1 开发者工具层** | docker CLI、docker compose | **前台** | 你敲命令的地方。痛点：人需要好用的接口，不想直接对着内核敲 |
| **层2 镜像构建层** | Dockerfile、`docker build`、BuildKit/Buildah/Kaniko | **车间** | 把代码+依赖造成分层镜像。痛点：环境不可复现 → 用分层+缓存解决 |
| **层3 高层运行时** | containerd、CRI-O | **经理** | 管镜像下载、容器生命周期。痛点：K8s 需要稳定的守护进程管理器，不需要 docker 全家桶 |
| **层4 低层 OCI 运行时** | runc、crun、Kata、gVisor | **建筑队** | 真正动手创建容器（调内核接口）。痛点：隔离与安全 → Kata/gVisor 提供强隔离 |
| **地基：操作系统内核** | Linux namespaces + cgroups | **地基** | namespaces 让每个房间"看不见别人"（隔离视图）；cgroups 给每个房间限水电（资源配额） |

**核心认知**：
- **OCI 标准**是分水岭——只要镜像符合 OCI 格式，任何层的实现都能替换（Docker 镜像可以在 containerd/Podman 上跑）。
- 四层**都可以自行选择/替换**，只要遵守 OCI。K8s 1.24 移除的只是 dockershim（层1 的 Docker 特有接口），不是 Docker 镜像格式。

## 3. 生态趋势与替代方案

"都不用 Docker 了"的真相：**Docker 镜像格式赢了（OCI），但 Docker 引擎本身正在被拆解替代**。

| 方向 | 方案 | 说明 |
|---|---|---|
| K8s 运行时 | **containerd**（~95% K8s 默认）、CRI-O | 轻量、专职管理容器，不再要 docker 全家桶 |
| 本地开发 | **Podman**（rootless/daemonless）、Finch、OrbStack、Rancher Desktop | Podman 无守护进程、非 root 更安全；Docker Desktop 商用收费催生替代品 |
| 构建工具 | BuildKit（Docker 内置新引擎）、Buildah、Kaniko（无 Docker 环境下构建，CI 常用） | 构建层也在去中心化 |
| 强隔离 | Kata Containers（轻量 VM）、gVisor（Google 的用户态内核） | 多租户不可信场景的"钢墙" |
| 未来 | WebAssembly/WASI | 秒级冷启动、更小粒度，边缘计算方向，尚在成长期 |

**结论**：学 Docker 的概念和镜像技术完全不过时——因为 OCI 标准是全行业通用的；换的只是"前台和经理"。

## 4. 多租户 / K8s / Pod

### 4.1 多租户（multi-tenancy）

**多租户 = 同一套系统同时服务多个互不信任的"客户"。**

- 单租户 = 独栋别墅：一栋楼一个住户，天然隔离但浪费。
- 多租户 = 小区公寓：一栋楼很多住户，共享水电地基（内核），靠门禁和墙壁（namespaces/cgroups）隔离。
- 风险叫**容器逃逸**：墙壁有漏洞，房客可能溜进别人房间。于是有 Kata/gVisor 这样的"钢筋混凝土墙"。

### 4.2 K8s 与"生产 K8s"

**K8s（Kubernetes）= 容器编排系统**：当容器多到几十上百个，人工管不动了，需要总部自动完成调度、故障自愈、扩缩容、滚动更新。

- **控制平面**：总部决策层（API Server、Scheduler、etcd…）——"哪家店开在哪、缺人了补谁"。
- **Node（工作节点）**：分店，每台机器上有 kubelet（分店经理）听总部指挥。
- **生产 K8s**：不是自己 `kubeadm` 手搓，而是用托管服务（云厂商的 ACK/EKS/GKE）或成熟发行版——总部把机房、高可用、升级全包了。

### 4.3 K8s 调度 Pod 而非容器

**Pod = 最小调度单位 = 一间套房**。套房里有若干房间（容器），共享客厅（网络/存储：同 IP、同端口空间、可挂共享卷）。

- 为什么不直接调度容器？因为有些紧密协作的进程（如主服务 + 日志收集边车）需要"同呼吸共命运"——一起调度、一起生死。
- **一个容器能跑多个进程吗？** 技术上可以（一个进程树），但**不推荐**：多进程会让"谁挂了重启谁"变得模糊，违背容器"一容器一职责"的设计。正确姿势是多容器组进一个 Pod，各自独立、各自可监控可重启。

## 5. 本项目分析：为什么是"单容器最简模型"

侦察 `E:\JDDataDisplay` 的结论：

| 特征 | 事实 | 对容器化意味着 |
|---|---|---|
| 后端 | FastAPI + uvicorn，单端口 `0.0.0.0:8000` | 暴露一个端口就够 |
| 前端 | Vue + Vite，FastAPI 同源托管 `frontend/dist` | 前端**构建产物**进镜像即可，不需要 Node 运行时 |
| 数据 | SQLite 单文件（`backend/app/data/`） | 挂个 Volume 就能持久化，不需要独立数据库容器 |
| 数据源 | `ResourceData/` 下的 Excel | 要 `COPY` 进镜像（或后续改挂卷） |
| 依赖 | `requirements.txt`（含 polars/pillow 等原生二进制） | 必须在 Linux 镜像内现装，不能拷 Windows 的 `.venv` |

**结论**：API + 页面 + 图片同端口同源、单文件数据库 → **单容器单进程**，是"单容器单 Pod"最简模型，不需要 Compose 多服务编排（一个 compose 文件只是为了让命令更好记）。

## 6. 容器化方案三件套（最终版）

### 6.1 `.dockerignore`（放项目根目录）

```gitignore
.venv
**/node_modules
**/__pycache__
*.pyc
.git
.scratch
.vscode
.workbuddy
docs
logs
preview
sample_data
DB.Browser.for.SQLite-v3.13.1-win64
backend/app/data
frontend/dist
```

**为什么排除这些**：`.venv` 是 Windows 编译产物，进 Linux 镜像必炸；`node_modules` 和 `frontend/dist` 应该在镜像内现造（可复现）；`backend/app/data` 运行时由 Volume 接管，不该烤死在镜像里；其余是纯垃圾，只为让"送料卡车"别超载。

### 6.2 `Dockerfile`（多阶段构建）

```dockerfile
# ============ 阶段1：构建前端（需要 Node） ============
FROM node:20-slim AS frontend-builder
WORKDIR /build
COPY frontend/package.json frontend/package-lock.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build

# ============ 阶段2：运行时（只需要 Python） ============
FROM python:3.12-slim AS runtime
WORKDIR /app
# 先拷依赖清单并安装（稳定层，命中缓存后改代码不用重装依赖）
COPY backend/requirements.txt ./backend/requirements.txt
COPY requirements.txt ./requirements.txt
RUN pip install --no-cache-dir -r requirements.txt

# 再拷业务代码 + 数据源（易变层）
COPY backend/ ./backend/
COPY ResourceData/ ./ResourceData/
COPY config.yml ./config.yml

# 从阶段1 搬构建好的前端产物（Node 和 node_modules 不进最终镜像）
COPY --from=frontend-builder /build/dist ./frontend/dist

# 运行时数据目录（实际数据由 Volume 接管）
RUN mkdir -p /app/backend/app/data

EXPOSE 8000
CMD ["python", "-m", "uvicorn", "backend.app.main:app", \
     "--app-dir", "/app", "--host", "0.0.0.0", "--port", "8000"]
```

**多阶段构建的精髓**：阶段1 是"临时工棚"（Node 造 dist），阶段2 才是"正式酒店"（Python 运行时）。末尾整个工棚连人带棚拆除，只把成品家具（dist）搬进酒店 → 最终镜像**自包含、可复现、不含 Node**。

### 6.3 `docker-compose.yml`

```yaml
services:
  jd-viz:
    build: .
    image: jddatadisplay:1.0
    ports:
      - "8000:8000"
    volumes:
      - jd_data:/app/backend/app/data
    restart: unless-stopped

volumes:
  jd_data:
```

## 7. docker-compose.yml 逐项解析

| 配置项 | 含义 |
|---|---|
| `services:` | 定义应用的容器列表，**每个服务对应一个容器** |
| `jd-viz:` | 服务名，也是容器名的前缀标识 |
| `build: .` | **用当前目录下的 Dockerfile 构建镜像**，而不是拉现成镜像 |
| `image: jddatadisplay:1.0` | 构建出的镜像命名为 `jddatadisplay:1.0` |
| `ports: - "8000:8000"` | **端口映射**：宿主机端口 8000 → 容器内部 8000。访问宿主机的 8000 端口时，就会自动转发到容器内的 8000 端口（应用监听的容器端口） |
| `volumes: - jd_data:/app/backend/app/data` | **声明命名卷** `jd_data` 挂到容器内的 `/app/backend/app/data`，数据持久化，容器删了数据还在 |
| `restart: unless-stopped` | 容器异常退出或宿主机重启后**自动重启**，除非手动停止 |
| 顶层 `volumes: jd_data:` | **显式声明**一个命名卷 `jd_data`，由 Docker 统一管理（存放在宿主的 `/var/lib/docker/volumes/` 下） |

## 8. docker compose up -d 解析

| 部分 | 含义 |
|---|---|
| `docker compose` | Docker 官方工具，**读取当前目录下的 docker-compose.yml** 来管理多容器应用 |
| `up` | **核心命令**：构建（如需要）+ 创建并启动 compose 文件里定义的所有容器，**同时创建**配置文件里声明的**卷和网络** |
| `-d` | `--detach` 的缩写，**后台运行模式**：容器启动后以"守护进程"方式持续运行，终端可以退出，不会打印日志到当前终端 |

**执行效果**：一次命令完成"**构建镜像 → 创建卷 → 启动容器**"，容器在后台持续运行，适合日常使用。

## 9. 等价的 docker run 逐参数解析

```bash
docker run -d --name jd -p 8000:8000 -v jd_data:/app/backend/app/data jddatadisplay:1.0
```

| 参数 | 含义 | 对应 compose 配置 |
|---|---|---|
| `docker run` | 创建并启动一个容器 | `services: jd-viz` |
| `-d` | 后台运行（detached），不占用当前终端 | `up -d` 的 `-d` |
| `--name jd` | 给容器起名 `jd` | compose 未显式写 `container_name`，默认"项目名-服务名"格式 |
| `-p 8000:8000` | 端口映射：宿主机 8000 → 容器 8000 | `ports: - "8000:8000"` |
| `-v jd_data:/app/backend/app/data` | 挂命名卷 `jd_data` 到容器内的路径，**首次使用会自动创建这个卷** | `volumes:` + 顶层 `volumes:` 声明 |
| `jddatadisplay:1.0` | 用哪个镜像启动（需先 `build: .` + `image: jddatadisplay:1.0` 构建好并打标签） | `build: .` + `image: jddatadisplay:1.0` |

> compose 版 vs run 版：功能等价，但 compose 把参数写进 YAML 可版本管理、可扩展多服务，日常首选；`docker run` 适合临时调试。

## 10. 0→1 十步执行流程

> 步骤 0 只做一次；1–2 是放文件；3 起才是构建。每步都给出"为什么"。

| 步骤 | 命令/动作 | 说明 |
|---|---|---|
| **0. 装 Docker Desktop** | 官网下载安装（Windows 需 WSL2） | 一次性的"前台 + 车间 + 经理"全家桶 |
| **1. 放 `.dockerignore`** | 内容见 6.1 | 先装好"装箱清单"，避免送料卡车超载 |
| **2. 放 `Dockerfile`** | 内容见 6.2 | 交出"装修图纸" |
| **3. 构建镜像** | `docker build -t jddatadisplay:1.0 .` | 车间开工。首次会下载基础镜像+装依赖，较慢；之后命中缓存秒级 |
| **4. 确认镜像** | `docker images` | 应看到 `jddatadisplay:1.0` |
| **5. 启动容器** | `docker run -d --name jd -p 8000:8000 -v jd_data:/app/backend/app/data jddatadisplay:1.0` | 或用 `docker compose up -d`（推荐，见第 8 节） |
| **6. 打开页面** | 浏览器访问 `http://localhost:8000` | 宿主机 8000 → 容器 8000，前后端同源 |
| **7. 摄入数据** | `curl -X POST http://localhost:8000/api/refresh` | 让后端读 `ResourceData/` 的 Excel 建库 |
| **8. 验证持久化** | `docker rm -f jd` 后重跑步骤 5，数据还在 | 因为数据在命名卷 `jd_data`，不在容器层 |
| **9. 随处可跑** | `docker tag jddatadisplay:1.0 <用户名>/jddatadisplay:1.0` → `docker push`；别处 `docker pull` + `docker run` | 镜像经 Registry 分发，从此"随地可跑" |
| **10. 展望 K8s** | 单 Pod 单容器 + Deployment | 容器多了再上编排（见第 16 节） |

## 11. 步骤 ↔ 四层架构对位表

| 你做的事 | 发生在哪一层 |
|---|---|
| 敲 `docker build` / `docker run` / compose 命令 | **层1 开发者工具层**（前台接单） |
| `docker build` 真正执行、生成镜像层 | **层2 镜像构建层**（车间造货） |
| 镜像下载、容器启停、生命周期管理 | **层3 高层运行时**（经理 dispatch） |
| 真正创建容器、设置隔离和资源限制 | **层4 低层 OCI 运行时**（建筑队动工，最终落到内核 namespaces/cgroups） |
| `POST /api/refresh` 后的业务逻辑 | **容器内部**（层几都管不着，那是你的应用代码） |
| `docker push/pull` 传镜像 | **Registry**（不在四层里，是镜像的"物流系统"） |

**记忆口诀**：**动镜像 = 层2；动容器 = 层3/4；敲命令 = 层1；业务逻辑 = 容器内；传镜像 = Registry。**

## 12. 进阶理解：构建上下文 ≠ 镜像层（COPY 段的意义）

**两个筐要分清**：

| 筐 | 名字 | 比喻 | 谁控制 |
|---|---|---|---|
| 筐A | 构建上下文 (build context) | 开往工地的**送料卡车** | `.dockerignore` 决定装什么 |
| 筐B | 镜像层 (image layers) | 盖好的**酒店房间** | `COPY`/`ADD` 决定摆什么 |

`docker build -t xxx .` 末尾的 `.` = "把当前目录当卡车拉去工地"。`.dockerignore` 只是**装箱清单**（别装 `.venv`、别装 200MB 的 SQLite 浏览器），纯粹防止卡车超载。

**但卡车上的料 ≠ 酒店里的家具**。镜像一开始只是空壳（基础镜像），不显式 `COPY`，Docker 绝不会自动把文件摆进房间。

所以方案里三行 COPY 各有使命：

- `COPY backend/` → 镜像里没代码，`uvicorn` 直接 `No module named backend`，容器起不来；
- `COPY ResourceData/` → `/api/refresh` 找不到 Excel 源，数据摄入必炸；
- `COPY config.yml` → 配置缺失，路径常量退化成默认值，违背"随处可跑"初衷。

**一句话**：`.dockerignore` 管"送不送料"，`COPY` 管"摆不摆货"——上下游关系，不是替代关系。

## 13. 为什么 pip 用 --no-cache-dir，npm ci 却不用

关键看**缓存最终待在哪个镜像里**：

- **`pip install --no-cache-dir`（阶段2，会被保留）**：pip 默认把下载的 wheel 缓存进 `~/.cache/pip`，这层**留在最终镜像**白白胀大几十上百 MB。`--no-cache-dir` = "装完别留包装盒"。
- **`npm ci`（阶段1，整体被丢弃）**：`npm ci` 本就强制清空 `node_modules`、严格按 lock 重装（可复现）；更关键的是阶段1 是临时工棚，末尾整体拆除，只有 `dist` 被 `COPY --from` 搬走。npm 缓存**根本走不到最终镜像**，加了也是给要炸的工棚做收纳。反而留着缓存还能加速下次重建。

> 💡 反直觉点：`--no-cache-dir` 不是"好就可以随便加"，而是**"加在会被保留的层才有意义"**。

## 14. 一定要显式 COPY 吗？"自动 copy" 的边界

**铁律**：文件进镜像，必须有人"点名"——没有"构建时自动把目录同步进镜像"的总开关。这是故意的：可复现、最小攻击面、显式即文档。

但确实有几种"看起来像自动"的写法（本质仍是你下了指令）：

| 写法 | "自动"在哪 | 适用场景 |
|---|---|---|
| `COPY . .` | 一行把整个构建上下文（除 `.dockerignore` 排除的）全搬进镜像 | 原型验证、偷懒 |
| `COPY --from=阶段名` | 多阶段之间自动传递上个阶段的产物 | 咱们方案搬 `dist` |
| `ADD` | 遇 `.tar/.tgz` 自动解压、`ADD <url>` 直接下载 | 要解压/拉 URL 时 |

**为什么本项目不用 `COPY . .`**：

1. **缓存命中线被腰斩**：把"稳定层（依赖安装）"放"易变层（代码）"之前，改代码时 pip 层命中缓存秒过；`COPY . .` 一把梭会让任何文件改动都触发依赖重装。
2. **安全隐患**：`.dockerignore` 只拦"卡车装货"；`COPY . .` 把卡车上剩下的全倒进房间——漏忽略 `.env`/密钥就直接烤进镜像。

**两个补充认知**：
- `.dockerignore` 是**全构建全局生效**的，不是按阶段隔离——所有阶段的 COPY 都读不到被忽略的路径（好在我们是现场 `npm run build` 造 dist，不依赖上下文里的 dist）。
- 官方建议：纯复制用 `COPY`，`ADD` 只留给"要解压 tar"或"要拉 URL"的场景，避免行为不透明。

## 15. 避坑清单汇总

1. **以为 `.dockerignore` 能代替 `COPY`** → 镜像空空如也、容器起不来 → 忽略清单只管"送料"，进镜像必须显式 `COPY`。
2. **把 `.venv`/`node_modules` 拷进镜像** → Windows 编译产物在 Linux 不兼容 → 它们进 `.dockerignore`，靠镜像内现装。
3. **多阶段忘写 `COPY --from=`** → 阶段产物没搬出来，前端 404 → 产出物必须显式搬运。
4. **给会被丢弃的阶段加 `--no-cache-dir` 反而拖慢重建** → 只在 runtime 这类保留层才需要。
5. **本机预构建 dist 再直接 COPY**（本项目踩过的雷）→ 干净克隆后无 dist，不可复现 → 多阶段构建现场造 dist，镜像自包含。
6. **`COPY . .` 且忘补 `.dockerignore`** → 镜像塞垃圾+泄密 → 要偷懒先写好 ignore，且放在依赖安装之后。
7. **把 `COPY . .` 放在 `pip install` 之前** → 改任何代码都重装依赖 → 永远"稳定层在前、易变层在后"。
8. **搞混 `*` 与 `**`（单星号 vs 双星号）** → Docker 的 `.dockerignore` 里 `*` **不跨目录**，所以 `*.pyc` 只兜根目录散落的 `.pyc`，子目录里的漏掉；要全层级覆盖应写 `**/*.pyc`。本项目没翻车，是因为 `**/__pycache__` 已把嵌套缓存目录整锅端了。⚠️ 注意：`.gitignore` 的规矩相反——无斜杠的 `*.pyc` 会**递归匹配所有子目录**，把 `.gitignore` 当 `.dockerignore` 直接套用极易漏忽略。

## 16. 下一步展望：上 K8s

本项目上 K8s 的最简形态：

```yaml
# deployment.yaml（示意）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: jd-viz
spec:
  replicas: 2
  selector:
    matchLabels: { app: jd-viz }
  template:
    metadata:
      labels: { app: jd-viz }
    spec:
      containers:
        - name: jd-viz
          image: <registry>/jddatadisplay:1.0
          ports: [{ containerPort: 8000 }]
          volumeMounts:
            - { name: jd-data, mountPath: /app/backend/app/data }
      volumes:
        - name: jd-data
          persistentVolumeClaim: { claimName: jd-data-pvc }
```

**要点**：单 Pod 单容器；SQLite 在多副本下会有写冲突，`replicas` 想扩到 2+ 前先把 SQLite 换成 PostgreSQL（项目里 `PG_DSN` 环境变量已预留了这条路）；K8s 的 PVC 替代 Docker 命名卷做持久化。
