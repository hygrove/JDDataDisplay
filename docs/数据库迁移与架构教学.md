# 数据库迁移与架构教学文档

> 本文档面向**学习阶段**的协作者，按「原理 → 过程 → 操作」三层讲清楚：
> 这次把「Excel/CSV 明细」改成「SQLite 存储」到底改了什么、为什么这么改、怎么跑起来。
> 读不懂代码没关系，先理解**为什么存在这一步**，再看**它干了什么**。

---

## 0. 一句话定位

原来：页面数据全部来自批处理把 Excel 清洗后生成的 **JSON 文件**。
现在：批处理先把 Excel 清洗后存进 **SQLite 单文件数据库**，再从数据库读出长表生成 JSON。
**对前端、对接口返回形状、对页面交互——零改动**。数据库只是换了一层「数据源之下」的存储。

---

## 1. 整个框架（数据怎么流）

```
            ┌──────────────────── 数据源（不进 git） ────────────────────┐
            │  ResourceData/                                              │
            │   ├─ 店铺spu登记信息.xlsx   （白名单闸门）                  │
            │   ├─ SPU商品名称映射表.xlsx （简名映射）                    │
            │   └─ 数据源表目录/                                          │
            │        ├─ *商品明细_*.xlsx   （每日增长的时序明细）          │
            │        └─ *推广数据_*.csv    （推广花费/成交金额）           │
            └────────────────────────────────────────────────────────────┘
                                  │ ① 摄入（Excel→清洗→长表→DB）
                                  ▼
            ┌─────────────────── run_batch.ingest_excel_to_db ───────────┐
            │  PopSpuExcelSource.fetch() 产出「统一长表」                  │
            │  → INSERT OR REPLACE 进 SQLite                              │
            │  → processed_file 记录每个源文件的 sha256（增量门控）        │
            └────────────────────────────────────────────────────────────┘
                                  │ ② 读长表
                                  ▼
            ┌──────────────────── backend/app/data/app.db ───────────────┐
            │  daily_detail(date, shop, spu, 16 个指标列)  UNIQUE(日期,店,SPU)
            │  processed_file(rel_path, content_hash, processed_at)        │
            └────────────────────────────────────────────────────────────┘
                                  │ ③ 取数（DB→长表）
                                  ▼
            ┌────────────────── pipeline.run_module (SqliteSource) ──────┐
            │  SqliteSource.fetch() 从 DB 读回统一长表                     │
            │  → transforms.build_module_data / build_summary 产出 JSON    │
            └────────────────────────────────────────────────────────────┘
                                  │ ④ 落盘 JSON（形状与以前完全一致）
                                  ▼
            ┌────────────────── backend/app/data/modules/*.json ─────────┐
            │  pop_spu_detail.json / .summary.json / manifest.json        │
            └────────────────────────────────────────────────────────────┘
                                  │ ⑤ HTTP
                                  ▼
                         FastAPI (/api/...)  →  前端 Vue3（零改动）

  图例：① 摄入=写库；② 读长表=查库；③④ 生成 JSON；⑤ 接口返回。
        前端从头到尾只认 JSON，完全不知道底下是 Excel 还是 SQLite。
```

**关键认知**：数据库不是「替代 JSON」，而是「替代 Excel 在管道里的位置」。
JSON 这层保留着，所以前端、API、缓存逻辑一行都不用动。

## 2. 配置实现过程（每个文件负责什么）

按「数据流经的顺序」讲，方便对照代码：

| 文件 | 角色 | 关键改动 |
|------|------|----------|
| `backend/jobs/config.py` | 全局常量 | 新增 `DB_PATH = DATA_DIR / "app.db"`（可用环境变量 `JD_DB_PATH` 覆盖） |
| `backend/jobs/sources/excel_source.py` | Excel 写入方 | **未改逻辑**，仍负责「读 Excel → 清洗 → 统一长表」，被摄入步骤调用 |
| `backend/jobs/db.py` | **新增** 持久化层 | `get_conn` / `ensure_schema`(建表) / `ingest_excel_to_db`(增量摄入) / `query_long_table`(读出) |
| `backend/jobs/sources/sqlite_source.py` | **新增** DB 读取方 | `SqliteSource.fetch()` 实现 `Source` 协议，从 DB 还原长表 |
| `backend/jobs/run_batch.py` | 批处理入口 | `run_once` 在 `run_all()` 前先调 `ingest_excel_to_db()` |
| `backend/jobs/pipeline.py` | 模块管线 | `default_registry` 的数据源由 `PopSpuExcelSource` 换成 `SqliteSource` |
| `backend/app/main.py` | Web 入口 | 启动钩子 `ensure_schema()`，保证表存在（幂等） |
| `scripts/setup_sample.py` | **新增** 样例桥接 | 把 `sample_data/` 复制到 `ResourceData/`，供异地/本地测试 |
| `.gitignore` | 仓库边界 | 加 `ResourceData/`（业务数据不进仓）、`*.db`（数据库不进仓） |

### 为什么 `db_source.py` 没被复用，而是新建 `sqlite_source.py`？
`db_source.py` 里已经有一个 **PostgreSQL 占位骨架**（`PostgresSource`），是给「将来京准通推广数据直连数据库」留的扩展位。
为了避免和未来的 PG 源撞名、也为了语义清晰，SQLite 读取方单独放在 `sqlite_source.py`（类 `SqliteSource`）。
写入方永远是 `excel_source.PopSpuExcelSource`，读取方是 `sqlite_source.SqliteSource`，两者产出**同形状**的长表，下游无感。

## 3. 实现原理（复杂逻辑由简单逻辑组成，每个都为解决一个痛点）

### 3.1 单文件嵌入式数据库：为什么是 SQLite
- **痛点**：原来数据散在多张 Excel/CSV，每天增长；要查询/增量/事务只能自己写文件拼接，脆弱且慢。
- **为什么单文件**：你要的是「轻量、在项目里、能随仓库走」。SQLite 一个 `.db` 文件既是数据库又是普通文件，不用起服务、不用配账号，完美贴合。
- **落点选择**：`backend/app/data/app.db`，和图片、JSON 同目录。该目录已被 `.gitignore` 忽略 → **数据库不进 git**，靠 `run_batch` 从 Excel 重建。

### 3.2 增量摄入 + 哈希追踪：只处理「变了的文件」
- **痛点**：每天数据源都在变，每次都全量重洗一遍慢且没必要。
- **机制**：`processed_file` 表记下每个源文件的**相对路径 + sha256**。
  - 本轮算出的所有哈希 == 上次存的历史哈希，且库里已有数据 → **直接跳过摄入**（真正的增量收益点）。
  - 任一文件哈希变了（新增/修改/删除）→ 用 `PopSpuExcelSource` 算出整张干净长表，`INSERT OR REPLACE` 写库，再刷新哈希。
- **为什么不「逐文件」增量，而是「变了就整表重算」**：
  白名单、名称映射是**全局过滤**——改一个 SPU 登记可能影响所有行。逐文件增量需要给每一行打「来源文件」溯源标签，复杂度高且易错。文件级哈希门控已经能在「没变就跳过」上拿到增量收益，剩余情况用**幂等 upsert** 保证正确。这是一个典型的「用一点正确性换复杂度」的取舍。
- **幂等性**：`UNIQUE(date, shop, spu)` + `INSERT OR REPLACE`，同一份数据反复跑结果一致，可放心重跑。

### 3.3 比率不入库：先求和再相除
- **痛点**：如果把「转化率」「客单价」「ROI」「推广占比」直接存进库，跨日/跨店汇总时**把它们相加或平均会得到错误结果**。
  例：周一转化 10/100=10%，周二 20/200=10%，区间真实应是 30/300=10%（凑巧一样）；
  换成周一 10/100、周二 20/100，区间真实是 30/200=15%，而 (10%+20%)/2=15% 只是巧合——换个数就错。
- **机制**：库里只存 16 个**可累加的原始列**（访客、成交、金额、推广费等），比率全部由下游 `transforms.compute_metrics` 在「先按维度求和、再相除」得到。
  这样「单日 / 店铺汇总 / 日期汇总 / 多日区间」四层口径**永远一致**。
- **此约束体现在哪**：`sources/base.py` 的 `LONG_COLUMNS` 里**没有**任何比率列；`db.py` 的 `daily_detail` 表也只建这 16 列。

### 3.4 数据源协议解耦：加一种数据源只要实现 `Source`
- **设计**：`sources/base.py` 定义 `Source` 协议——任何数据源只要实现 `name` 和 `fetch() -> 长表` 即可接入。
  本次新增 `SqliteSource` 就是这么接入的，下游 `pipeline` 完全不用改。
- **读写两方**：`PopSpuExcelSource`（写库用）、`SqliteSource`（读库用）是一对，都产出 `LONG_COLUMNS` 形状。
  将来要接 PostgreSQL（`db_source.PostgresSource` 骨架已留好位），同样实现 `fetch()` 即可，零改动下游。

### 3.5 数据 / 代码分离：什么进 git，什么不进
- **`ResourceData/` 不进 git**：每日增长的业务 Excel/CSV/图片，体积大且含业务数据。
- **`*.db` 不进 git**：SQLite 是跑出来的产物，可随时重建。
- **`sample_data/` 进 git**：只留**少量样例表**（白名单 + 名称映射 + 一个店的明细/推广 + 一张图），让别人克隆后能立刻跑通。
- **桥接脚本 `setup_sample.py`**：异地克隆后先 `python scripts/setup_sample.py` 把样例铺到 `ResourceData/`，再 `python -m backend.jobs.run_batch` 生成 `app.db` 与 JSON。
  > ⚠️ 若 `ResourceData/` 此前已被提交进 git，需先 `git rm -r --cached ResourceData` 解除跟踪，新规则才会生效。

## 4. 操作（怎么跑）

### 4.1 本地（已有真实 ResourceData）
```bash
# 1) 跑批处理：先把 Excel 增量写入 SQLite，再生成 JSON
python -m backend.jobs.run_batch
# 2) 启动服务（按需，服务启停由你掌握）
uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```
首跑全量摄入；之后再跑，只要数据源没变就会打印 `reason=unchanged` 跳过摄入。

### 4.2 异地 / 新机器（只有仓库，没有业务数据）
```bash
# 1) 用样例数据铺盘
python scripts/setup_sample.py
# 2) 跑批处理生成 app.db 与 JSON
python -m backend.jobs.run_batch
# 3) 起服务看页面
uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```

### 4.3 验证摄入是否生效
- 看 `run_batch` 日志里的 `[db] 摄入：{...}`，`changed=True` 且 `rows>0` 表示写入成功。
- 直接看文件：`backend/app/data/app.db` 已生成。
- 进库查询（可选）：用任意 SQLite 工具 `SELECT COUNT(*) FROM daily_detail;` 看行数。

## 5. 常见坑 & 排错

1. **页面空 / 报「请先运行批处理」**：八成是 `run_batch` 没跑，或 `setup_sample.py` 没铺数据。`app.db` 为空时 `SqliteSource.fetch()` 返回空长表，JSON 也就是空的。
2. **改了数据源但页面没变**：确认 `run_batch` 重新跑过（摄入会被哈希门控；若文件哈希真的变了会重算）。`/api/refresh` 也会触发重跑并清缓存。
3. **白名单闸门**：只有「店铺spu登记信息.xlsx」里登记的 SPU 才会出现；新增店铺/SPU 先登记再跑批。
4. **`~$*.xlsx` 锁文件**：Excel 打开时产生，批处理已过滤；提交仓库前关掉 Excel。

## 6. 一句话回顾（便于记忆）

> Excel 是「喂数据的人」，SQLite 是「存数据的抽屉」，JSON 是「端给前端的菜」。
> 这次只是把菜的原料从「临时摆在桌上（Excel）」搬进了「带标签的抽屉（DB）」，
> 厨师（pipeline）和食客（前端）的感觉完全一样——但抽屉能锁、能增量、能查，稳多了。
