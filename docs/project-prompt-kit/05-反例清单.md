# 一、数据口径类

## 1-1 比率的聚合方式

**错在哪**：比率不可加，但在明细行算好后又被求和/取平均。

```python
# ❌ 明细行算好比率，后面直接求和
df.with_columns((pl.col("buyers") / pl.col("visitors")).alias("rate"))
df.group_by("shop").agg(pl.col("rate").mean())    # → 27.5%，完全错
```

```python
# ✅ 先 sum 分子分母，再相除
def aggregate(df, keys):
    out = df.group_by(keys).agg(
        pl.col("visitors").sum(),      # 先分别求和
        pl.col("buyers").sum(),
    )
    return compute_metrics(out)          # 再相除
```

**验证**：两天转化率 5%（5/100）和 50%（50/10）→汇总必须是 `55/110 = 50%`，不是 `27.5%`。

## 1-4 隐藏分子没参与累加

**错在哪**：只遍历指标清单累加，而某字段是比率的分子但不在清单里。

```ts
// ❌ 只累加清单内的指标 → search_clicks 恒为 0 → 点击率恒为 0%
for (const m of METRICS) {
  for (const p of points) sums[m.key] += p[m.key] ?? 0;
}
```

```ts
// ✅ 累加集合 = 所有 sum 指标 ∪ 所有 ratio 的分子/分母
const sumKeys = new Set<MetricKey>();
for (const m of METRICS) {
  if (m.agg.kind === "sum") sumKeys.add(m.key);
  else { sumKeys.add(m.agg.num); sumKeys.add(m.agg.den); }
}
for (const p of points) {
  for (const k of sumKeys) {
    const v = p[k];
    if (typeof v === "number" && !Number.isNaN(v)) sums[k] = (sums[k] ?? 0) + v;
  }
}
```

**验证**：`agg([{search_clicks:10, search_impressions:1000}]).search_click_rate === 0.01`。

## 1-5 百分点判定用错字段

**错在哪**：按聚合算法判定，导致客单价被记成百分点。

```ts
// ❌ 按 agg.kind 判定 → 客单价（ratio 聚合、单位金额）算出 +2158.00pt
const isPercent = (m: MetricSpec) => m.agg.kind === "ratio";
```

```ts
// ✅ 按单位判定；字段名也要体现这个区别：ratio ≠ 百分比
const isPercent = (m: MetricSpec) => m.format === "percent";
```

**真实数字对照**：

| 指标 | `agg.kind` | `format` | ❌ 按 kind | ✅ 按 format |
| --- | --- | --- | --- | --- |
| 成交转化率 | ratio | percent | `−0.35pt` ✓ | `−0.35pt` ✓ |
| **客单价** | **ratio** | **currency** | **`+2158.00pt`** ✗ | **`+¥21.58`** ✓ |
| ROI | ratio | decimal | `−0.38pt` ✗ | `−0.38` ✓ |
| 商品访客数 | sum | number | `−1,067` | `−1,067` ✓ |

⚠️ **字段命名建议**：用 `isPercent` 而不是 `isRatio`，
让字段名本身提醒「这是单位判断，不是算法判断」。

## 1-6 两个来源导致自相矛盾

**错在哪**：表头天数用原始区间，取数用对齐后区间。

```ts
// ❌ 两个 computed 用了不同的来源
const daysMap = computed(() => dayCountInRange(rawRanges[mo]));   // 31 天
const rangeMap = computed(() => alignedRanges);                  // 30 天
// → 「数据已按 30 天截取、表头却写 31 天」
```

```ts
// ✅ 都从对齐后的区间派生
const rangeMap = computed(() => alignAll(rawRanges));            // 唯一事实来源
const daysMap = computed(() => {
  for (const mo of selectedMonths) out[mo] = dayCountInRange(rangeMap[mo]);
  return out;
});
// 取数也用 rangeMap → 表头、提示、取数三者天然一致
```

**通用原则**：任何时候出现「A 处显示 X，B 处算 Y，两者应该一致」，
就检查它们**是否来自同一个来源**。这是前端口径事故第一大来源。

## 1-7 对齐的方向性 bug

**错在哪**：只拿两个区间比，只截一个；且遇到「不反向延长」就原样返回。

```ts
// ❌ 只截 A；当 A 天数更多时截断点越过 A 的 end → 走进else 分支原样返回 → 完全没截
function trim(a, b) {
  const d = dayCount(a) - dayCount(b);
  if (d > 0) return shift(a, -d);      // 只截左边
  if (d < 0) return b;                 // ❌ 右边完全没处理
  return [a, b];
}
```

```ts
// ✅ 所有区间对齐到全局最短，且绝不反向延长
function alignAll(ranges: MonthRange[]) {
  const target = Math.min(...ranges.map(r => dayCountInRange(r)));
  return ranges.map(r => {
    const own = dayCountInRange(r);
    const t = Math.min(target, own);          // 越界收敛回自身 end
    return trimToDays(r, t);                  // ⚠️ 绝不为某个区间反向延长
  });
}
```

**验证（必须双向测）**：

|场景 | 期望 |
| --- | --- |
| 8月31天 + 9月30天 | 两者都取前 **30** 天 |
| 9月30天 + 8月31天（顺序反） | 同上，**结果必须一致** |
| 30天 vs 31天，目标 30 | 短月**绝不能**被延长到 31天 |

**扩展**：多个区间取**全局最小**，不要两两比较。

## 2-6 状态从单值改多值时漏改的四处

**错在哪**：把「单值展开」改成「多行可同时展开」，只改了状态声明，漏了连带假设。

| # | 连带处 | ❌ 单值写法 | ✅ 多值写法 |
| --- | --- | --- | --- |
| 1 | 状态 | `Ref<string \| null>` | `Ref<Set<string>>`，**用新 Set 替换**才触发更新 |
| 2 | 几何计算 | 单个 `computed` | **按 key 取的普通函数**（每行各算自己的） |
| 3 | 尺寸观察 | 只跟最后一个元素 | `Set` 累积全部，宽度取**最大值** |
| 4 | SVG id | 共用 id | 按行加后缀 |

**第 1 条的坑**：原地 `add` / `delete` **不触发** Vue 变更检测。

```ts
// ❌ 原地改，UI 不更新
function toggleRow(key: string) { expandedRowKeys.value.add(key); }
// ✅ 用新 Set 替换
function toggleRow(key: string) {
  const next = new Set(expandedRowKeys.value);
  next.has(key) ? next.delete(key) : next.add(key);
  expandedRowKeys.value = next;      // ← 触发变更检测
}
```

**模板里造局部别名**（因为 computed 变成了函数调用）：

```html
<template v-for="tl in [tlOf(r.key)]">
  <div v-if="tl"><svg :viewBox="`0 0 ${tl.W} ${tl.H}`">...</svg></div>
</template>
```

## 2-8 transform 与 fill 写在同一条 transition

## 3-1 toISOString 时区

**错在哪**：转UTC，东八区凌晨差一天。

```ts
// ❌ 本地 2026-10-01 00:30 → UTC 2026-09-30 16:30 → 日期差一天
const key = d.toISOString().slice(0, 10);
```

```ts
// ✅ 本地时间 + 手动补零
const pad = (n: number) => String(n).padStart(2, "0");
const key = `${d.getFullYear()}-${pad(d.getMonth() + 1)}-${pad(d.getDate())}`;
```

⚠️ 这个 bug **只在东八区凌晨出现**，极难复现。

**配套**：日期是定长 `YYYY-MM-DD`，**字典序即时间序**，可直接字符串比较，
不需要 `Date` 解析（更快也更少出错）。

## 3-4 增量粒度选错

**错在哪**：逐文件增量，但过滤是全局的。

```python
# ❌ 逐文件增量：改一条白名单登记，无法判断哪些已入库的行该被移除

```

```python
# ✅ 文件集级哈希门控：任一变化 → 重算整张干净表 + 幂等 upsert
hashes = {_rel(root, p): _sha256(p) for p in files}
if hashes == old and _count_rows() > 0:
    return {"changed": False, "reason": "unchanged"}   # ← 真正的增量收益点
df = source.fetch()
_upsert_long_table(df)                                 # UNIQUE 键 + INSERT OR REPLACE
```

**为什么**：白名单 / 名称映射是**全局过滤**，逐文件增量需行级溯源，复杂度高且易错。
文件级门控已能拿到「数据没变就跳过」的收益，其余用幂等 upsert 保证正确。

```python
def port_busy(port: int = 8000) -> bool:
    with socket.socket() as s:
        return s.connect_ex(("127.0.0.1", port)) == 0

if port_busy():
    open_browser(); sys.exit(0)
```

⚠️ **进程枚举必须限定 `python.exe` / `pythonw.exe`**——
否则启动它的外壳命令行同样含脚本名，会「把自己当另一个实例」自我拦截。

## 3-10 断言的期望值算错

**错在哪**：期望值按未舍入的精确值写，浮点对不上。

```js
// ❌ 期望值写成 0.3333333333，容差 1e-9
assert(Math.abs(rate - 0.3333333333) < 1e-9);
// → FAIL，但代码是对的
```

```js
// ✅ 期望是舍入结果时，容差按舍入粒度给
assert(Math.abs(rate - 0.3333) < 0.005);
```

```js
// ✅ 浮点一律先四舍五入再比较
const round4 = (v) => Math.round(v * 1e4) / 1e4;
assert(round4(rate) === 0.3333);
```

**铁律**：⚠️ **断言失败时先怀疑测试本身**——
历史上多次 FAIL 都是期望值写错（浮点未考虑舍入、符号逻辑写反）。
**写断言时先手算一个具体数字**，不要「看着代码推期望」。
