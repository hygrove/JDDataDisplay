# 架构契约

> 配套 `00-主提示词.md`。这份文档描述**结构**：分层、数据流、扩展点、目录布局、API 契约。
> 业务细节（指标名、店铺概念、Excel 列名）按你的实际数据替换。

---

## 一、为什么是这个架构

一句话：**让「数据从哪来」「怎么算」「怎么给」「怎么看」四件事各自独立，换任何一件都不影响其他三件。**

具体解决四个痛点：

| 痛点 | 架构解法 |
| --- | --- |
| 数据源格式各异（Excel/CSV/数据库），每加一种就要改一遍全链路 | **Source 协议**：所有来源规整成同一张长表，下游不关心来源 |
| 加一个新模块要写前后端一整套页面 | **模块注册表**：模块 = 一份配置，前端不写新页面 |
| 加一个指标要改 4 处代码 | **指标清单为唯一事实来源**：卡片/列/图表/对比项全部派生 |
| 后端改了字段前端崩、前端加了字段后端没返| **长表只存可累加原始指标**，派生指标由聚合层统一算 |

## 二、五层分层

```
┌─────────────────────────────────────────────────────────┐
│ ① 数据源层    sources/                                    │
│    Excel / CSV / 数据库 → 规整成统一长表                │
│    职责：脏数据进来，标准长表出去。完全不懂业务口径       │
└───────────────────────┬─────────────────────────────────┘
                        │统一长表（只含可累加原始指标）
                        ▼
┌─────────────────────────────────────────────────────────┐
│ ② 持久层      db.py                                       │
│    干净长表落 SQLite + 源文件哈希追踪                    │
│    职责：增量摄入、幂等写入。删了可从源文件全量重建       │
└───────────────────────┬─────────────────────────────────┘
                        │读出干净长表
                        ▼
┌─────────────────────────────────────────────────────────┐
│ ③ 聚合层      transforms.py  ★ 口径唯一事实来源          │
│    长表 → 层级明细 JSON + 汇总 JSON                      │
│    职责：分组求和、派生比率、产出前端可直接消费的结构     │
└───────────────────────┬─────────────────────────────────┘
                        │JSON 落盘
                        ▼
┌─────────────────────────────────────────────────────────┐
│ ④ API 层       api.py + main.py                          │
│    读 JSON → REST + 单端口托管 SPA/图片 + 导出 xlsx      │
│    职责：不碰口径，只做鉴权/序列化/缓存/导出             │
└───────────────────────┬─────────────────────────────────┘
                        │HTTP
                        ▼
┌─────────────────────────────────────────────────────────┐
│ ⑤ 前端        Vue3 SPA                                    │
│    指标清单驱动渲染 + Pinia 状态 + 虚拟列表              │
│    职责：交互与可视化。口径由后端保证，前端只做区间聚合   │
└─────────────────────────────────────────────────────────┘
```

**分层纪律**：

- ① 不知道比率是什么（比率不进长表）
- ② 不知道指标含义（只管存取）
- ③ **只有这里知道口径**
- ④ 不做业务计算
- ⑤ 只做「展示前端的区间聚合」，**且必须与 ③ 口径一致**（见 R-01）

## 三、数据流全链路

```
<数据源目录>/
├── {店铺名}_商品明细_{日期范围}.xlsx      ← 商品维度
├── {店铺名}_推广数据_{日期范围}.csv       ← 推广维度
├── 商品名称映射表.xlsx                    ← SPU → 简化名（可选增强）
└── 店铺spu登记信息.xlsx                   ← 白名单闸门
        │
        │ ①清洗：跳过 ~$锁文件 → 列名映射 → 去重 → 左连接补数据
        │        → 白名单过滤 → 名称映射 → 补齐列序
        ▼
   统一长表（16 列：5 维度 + 11 可累加指标）
        │
        │ ② 增量：全部源文件 sha256 比对
        │    ├─ 全一致且库里有数据 → 跳过（收益点）
        │    └─ 任一变化 → 重算整表 + INSERT OR REPLACE（幂等）
        ▼
   SQLite: daily_detail(明细长表) + processed_file(哈希追踪)
        │
        │ ③ 聚合：group_by(维度) → sum(可累加) → compute_metrics(比率)
        ▼
   backend/app/data/
   ├── manifest.json                       ← 模块清单
   ├── modules/{id}.json                   ← 层级明细（店铺→商品→日期→指标）
   ├── modules/{id}.summary.json           ← 图表汇总
   ├── status.json                         ← 上次批处理状态
   ├── app.db                              ← SQLite
   ├── images/{商品号}.png                 ← 原图
   └── thumbs/{96,120,180}/{商品号}.{avif,webp}  ← 多尺寸缩略图
        │
        │ ④ API：lru_cache 读 JSON → REST
        ▼
   单端口 8000: /docs  /api/*  /images  /thumbs  /(SPA)
        │
        │ ⑤ 前端：指标清单派生列/卡/图；Pinia 管筛选与分页
        ▼
   页面
```

**关键设计点**：

1. **JSON 是批处理与 API 之间的契约边界**。批处理只管产出 JSON，API 只管读 JSON。
   想换数据库 / 换源格式，前端与 API 完全不动。
2. **图表汇总不按店铺拆文件**。若拆，文件数随店铺线性膨胀。
   改为在 date 字段带店铺前缀（`店铺A|2026-09-17`），前端按需过滤拆分。
3. **缩略图单独产出**。原图常 0.9~3MB，而卡片只有 96/120/180px，
   直接下原图会拖垮首屏。生成 AVIF+WebP 双格式多尺寸，幂等重算。

## 五、扩展点矩阵（**可扩展性的核心**）

这是「以后加东西不用动主干」的保证。四类扩展各改一处：

| 要加什么 | 改哪些文件 | 写不写新代码 |
| --- | --- | --- |
| **新数据源**（如从ERP 取数） | ① `sources/` 新建模块实现 Source 协议<br>② `pipeline.py` 的源列表加一项 | 40 行左右，**不动下游** |
| **新模块**（如「店铺维度总览」） | ① `pipeline.py` 的 `ModuleSpec` 加一项<br>② 前端 `modules/index.ts` 注册表加一项<br>③ `metrics.ts` 加该模块独有指标 | **不写新页面** |
| **新指标** | ① 前端 `metrics.ts` 加一条 spec<br>② 后端 `models.py` 加字段<br>③ 后端 `api.py` 字段白名单加一项 | 卡片/列/图/配置面板**自动派生** |
| **换数据库**（SQLite → PostgreSQL） | ① 实现同一个 Source 协议从 PG 读<br>② 改 `config.py` 的连接配置<br>③ 建表 SQL 方言适配 | 下游全不动 |

### 5.1 Source 协议（扩展点 ①的契约）

```python
class Source(Protocol):
    """数据源协议：把任意来源规整成「统一长表」。"""
    name: str
    def fetch(self) -> pl.DataFrame:
        """拉取并规整数据，返回统一长表。

        Returns:
            pl.DataFrame: 列集合等于 LONG_COLUMNS 的长表；
                数值列允许为 None（表示该项缺失）。

        Raises:
            源文件不存在 / 格式非法 / 鉴权失败时抛出，
            建议带上 data源 name 便于定位。
        """
        ...
```

**约定输出列（缺失的列补 None）**：

```
维度列（5）：shop, date, spu, spu_name, category
可累加指标（11）：visitors, buyers, orders, items, amount,
              search_impressions, search_clicks,
              promotion_cost, promotion_amount,
              refund_orders, refund_amount
```

**⚠️ 两条纪律**：

1. **派生比率绝不在长表里**（`conversion_rate` / `avg_price` / `search_click_rate` /
   `roi` / `promotion_ratio`）。源表里即使有同名列也不要——源表的比率是「当日比率」，
   求和或取平均都错。统一由聚合层重算（R-03）。
2. **缺列补 None，不要让下游猜**。实现里：

```python
for col in LONG_COLUMNS:
    if col not in df.columns:
        df = df.with_columns(pl.lit(None).alias(col))
return df.select(LONG_COLUMNS)   # 严格列序
```

多源纵向拼接用 `diagonal_relaxed` 模式——它允许各源列集合不同、缺失列自动补 null，
正好适配「Excel + 数据库推广数据」的场景。

### 5.2 ModuleSpec（扩展点 ②的契约）

```python
@dataclass
class ModuleSpec:
    module_id: str                    # 唯一标识，同时决定产出文件名
    title: str                        # 中文名
    description: str                  # 进 manifest 供前端展示
    sources: list[Source] = field(default_factory=list)
    top_n: int = config.SUMMARY_TOP_N
```

### 5.3 MetricSpec（扩展点 ③的契约）

```ts
interface MetricSpec {
  key: MetricKey;              // 必须与后端字段名一致
  icon: string;
  title: string;               // 展示名
  format: "number" | "currency" | "percent" | "decimal";
  group: "detail" | "promo" | "extra";
  width: number;               // 表格列宽
  color: string;               // 图表配色
  defaultOn: boolean;          // 是否默认勾选
  agg: { kind: "sum" }
     | { kind: "ratio"; num: MetricKey; den: MetricKey };   // 聚合方式
  compare: keyof CompareGroup | null;   // 工作日/节假日对比取哪个字段
  compareLabel?: string;
}
```

**⚠️ `agg` 只有两种形态**，这是「先求和再相除」得以在前后端同时成立的载体：
后端 `aggregate` 先sum 分子分母再 `compute_metrics`，前端 `aggregateMetrics`
先 `sumRawMetrics` 再按 `agg.num/den` 相除——**结构完全对称**。

**⚠️ `isPercent` 而非 `isRatio`**：判断「要不要记百分点」看的是**单位**不是算法。
客单价是 ratio 聚合但单位是金额，字段名必须体现这个区别（见 R-05）。

## 六、API 契约

| 方法 | 路径 | 要点 |
| --- | --- | --- |
| GET | `/api/manifest` | 模块清单（各模块店铺/日期区间/商品数） |
| GET | `/api/module/{id}/rows` | 分页明细。支持 `start`+`end`；返回**逐日数组**，缺失日指标为 `null` |
| GET | `/api/module/{id}/summary` | 图表汇总 |
| GET | `/api/module/{id}/spu/{spu}/analysis` | 单品分析（趋势/工作日节假日/洞察）。支持 `start`+`end` |
| POST | `/api/module/{id}/export` | 导出**全量**数据为 xlsx（不受前端分页影响） |
| GET | `/api/status` | 上次批处理状态 |
| POST | `/api/refresh` | 重跑批处理 + 清缓存 |

### 6.1 明细行 JSON 形状（前端渲染的依据）

```jsonc
{
  "shop": "店铺A",
  "spu": "100...",
  "spu_name": "...",
  "category": "...",
  "image": "/thumbs/120/100....webp",
  "date": "2026-09-17",     // 单日模式=该日；区间模式为空串
  "metrics": { /* 单日模式=当天的值；区间模式全 null */ },
  "days": [                // 区间模式核心：逐日数据
    { "date": "2026-09-17", "metrics": { "amount": 1520.1 } },
    { "date": "2026-09-16", "metrics": { "amount": null } }   // 缺失 = null，不是 0
  ]
}
```

**⚠️ `null` 与 `0` 的区别是硬约定**：
`null` 表示「该项当天没有数据」，`0` 表示「有数据但值为 0」。
前端必须区分：缺数据不算进平均，累加时跳过（见 R-04）。

### 6.2 导出的硬约束

- **全量导出，不受分页限制**——用户筛完条件要的是完整数据。
- **比率类总计 = 分子分母总量相除**（不是逐日比率求平均），且**用字体色标记**，
  表头注明「总计（某色为总量平均值）」。
  ⚠️ **不用底色**：底色会压住数字，运营还要二次加工这个表。
- **图片列纵向合并**嵌入缩略图。
  ⚠️ Excel 图片是浮层drawing、**没有 valign 属性**，须按「块高 − 图片高」算锚点偏移实现垂直居中。
- **元信息列只合并第一列**，保持整表可排序/求和。
- 数值保留两位小数，**整数不带 `.0``（避免Excel 把编号识别成文本）。

## 七、前端架构要点

### 7.1 两种展示形态的自动切换

**单日模式**（区间起止同一天）是**区间模式只有 1 天列的特例**。
由日期区间自动决定，不需要手动切模式开关——这是减少状态数量与 bug 面 的关键设计。

### 7.2 状态管理纪律

- **store 按页面职责拆**：模块页 store / 指标配置 store / UI store。
- **⚠️ 离开页面时reset**。跨页不要依赖 store 里的派生 getter——
  模块页 `onUnmounted` 会 reset，其他页面读到undefined。
  需要在别处用时，从 `prop` 或 `route` 自查manifest。
- **localStorage 按模块 id 分开存**，key 带结构版本（`v1`）以便将来迁移；
  隐私模式下降级为默认值，不阻断功能。

### 7.3 长列表

用 `@tanstack/vue-virtual` 虚拟滚动。
⚠️ **虚拟滚动与横向滚动的矩阵区域会打架**（容器尺寸被虚拟化接管）。
参考实现的做法：每页 300 行（后端上限 500），翻页追加而非无限滚动——
牺牲一点流畅度，换来矩阵列对齐可控 + 后端分页简单。

### 7.4 图表

- `vue-echarts` **按需引入**，禁止全量导入。
- **双轴组合图**的量程规则：两个都是百分比时**左右轴共用同一量程**，
  否则刻度无法直接比较，读者要心算换算。
- y 轴百分比指标的刻度标签统一以**百分格式**展示（如 `6.6%`），tooltip 按各序列自身格式。
- 警戒线类需求（用户可调阈值）做成**页面输入框 + 实时生效**，不写死在配置里。

## 八、静态资源的两套机制（易混）

| 类型 | 位置 | 机制 | 换文件时 |
| --- | --- | --- | --- |
| **装饰图**（LOGO、空态插画、背景） | `frontend/public/` | 构建时**原样拷贝**到 dist 根，**文件名不哈希** | 替换文件内容即可，**不用改代码**（文件名保持稳定） |
| **业务图**（商品图） | `backend/app/data/images` | 批处理产出，FastAPI 挂 `/images`（原图）与 `/thumbs`（缩略图） | 换数据源图片，重跑批处理 |

⚠️ 装饰图用稳定命名（如 `empty-alien.svg` 而不是 `alien-v2.svg`），
这样换图只替换内容、不动代码，也不会因为文件名变化而全量失效。

## 九、配置哲学

`config.py` **只放常量，不放逻辑**，且**全部支持环境变量覆盖**：

```python
BACKEND_DIR = Path(__file__).resolve().parent.parent      # 项目根可任意改名/移动
DATA_DIR    = Path(os.getenv("JD_DATA_DIR", BACKEND_DIR / "app" / "data"))
DB_PATH     = Path(os.getenv("JD_DB_PATH",  DATA_DIR / "app.db"))
SOURCE_DIR  = Path(os.getenv("POP_SOURCE_DIR", BACKEND_DIR.parent / "<业务数据目录>"))
PG_DSN      = os.getenv("PG_DSN", "")        # 留空 = 跳过数据库源
```

**这带来的收益**：换机器、换盘符、迁 Docker、换数据目录，**都不用改代码**。

⚠️ **不要把绝对路径烧进计划任务 / 启动脚本 / Docker 镜像**：
- 解释器路径在运行期按候选列表解析；
- 刷新地址走环境变量；
- 项目根由 `__file__` 推导。

**零配置文件原则**：所有配置项都有默认值，**新机器零配置即可跑通**
（示例：`config.yml` 是空 `{}`，不需要 `.env`）。

⚠️ **脚本文件的编码坑**：Windows PowerShell 5.1 / cmd 按 GBK 读 UTF-8 中文，
`.ps1` / `.bat` / `.vbs` 内容**必须纯ASCII**（中文注释会吞行导致解析失败）。
`.py` / `.pyw` 无此坑——中文注释安全。
