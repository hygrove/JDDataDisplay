# 项目搭建提示词包

> 面向「用AI agent 搭建一个电商数据可视化平台」的场景。
> 这套文档从 `JDDataDisplay` 项目逆向提炼而成——不是照抄文档，
> 而是从代码、注释、变更记录、踩坑史里挖出**隐式契约**。

---

## 一、怎么用

### 最小用法（3 份）

给agent 这三份，能搭出结构正确、口径不漂的项目：

| 文件 | 作用 |
| --- | --- |
| `00-主提示词.md` | 角色、技术栈硬约束、铁律清单、六阶段任务与验收判据 |
| `02-口径铁律.md` | ★ 最不可替代——每条约束的「为什么错 + 正确写法 + 真实数字」 |
| `03-验收清单.md` | 可执行的验证闭环（回归断言 + 真实浏览器实测） |

### 完整用法（6 份）

再补三份，适合需要迁移部署或团队协作：

| 文件 | 作用 |
| --- | --- |
| `01-架构契约.md` | 五层分层、数据流、扩展点矩阵、目录布局、API 契约 |
| `04-迁移手册.md` | 环境变量、异地部署、换数据库、跨平台、故障排查表 |
| `05-反例清单.md` | ★ 正反对照代码——给对错比给原则有用 |

### 放进你的项目

建议存到`<项目>/docs/project-prompt-kit/`，然后在`AGENTS.md` 或
`CLAUDE.md` 里加一句指路：

```markdown
## 项目搭建 / 大改造时
动手前先读 `docs/project-prompt-kit/00-主提示词.md`（铁律清单是硬约束），
涉及口径与前端正确性时补读 `02-口径铁律.md` 与 `05-反例清单.md`，
交付前按 `03-验收清单.md` 逐项验证。
```

## 二、六份文档的分工

```
00-主提示词   ← 入口：角色 / 技术栈 / 铁律清单 / 六阶段任务 / 验收判据
      │
      ├── 01-架构契约   结构：分层 / 数据流 / 扩展点 / API
      │
      ├── 02-口径铁律★ 约束：A类数据口径 / B类前端 / C类工程纪律
      │                （每条含「为什么错 + 正确写法 + 真实数字」）
      │
      ├── 03-验收清单★验证：回归断言 / 浏览器实测 / 一致性校验
      │
      ├── 04-迁移手册   部署：环境变量 / 异地链路 / 换库 / 跨平台
      │
      └── 05-反例清单★ 纠错：❌ 错误代码 ↔✅ 正确代码
```

★ = 建议**必读**。这三份承载了文档与原则之外的东西——
**具体的失败数字和错误代码**，是让 agent 避开陷阱的关键。

## 三、这份提示词的设计取舍

### 3.1 为什么不写成「一个大prompt」

800 行的提示词，agent 在第 300 行就开始丢约束。
所以做了三件事：

1. **按需加载**：主提示词只放角色/约束/任务，具体结构与验证拆到独立文件；
2. **关键约束重复三次**：开头列铁律清单 → 各阶段重申相关铁律 → 收尾再复述；
3. **正反对照优先于原则陈述**：「viewBox 要 1:1」不如「写死会导致 scaleX=1.979」。

### 3.2 铁律全部来自真实事故

没有一条是假想风险。举几个例子：

| 铁律 | 来源事故 |
| --- | --- |
| R-01 先求和再相除 | 5% 与 50% 平均成 27.5% |
| R-04 隐藏分子参与累加 | 搜索点击率长期恒为 0.00% |
| R-05 百分点按单位判定 | 客单价算出 `+2158.00pt` |
| R-06 单一事实来源 | 已按 30 天截取、表头写 31 天 |
| R-07 绝不反向延长 | 较短月在右侧时对齐完全失效 |
| R-08 缩进只作用文字 | 斑马纹「突然断掉、没延伸到边缘」 |
| R-09 SVG 1:1 | `scaleX=1.979`，调小字号只是治标 |
| R-11 id 文档级唯一 | 多行箭头消失，不报错、构建也过 |
| R-12 CSS 特异性 | 绿涨红跌「代码写了没生效」 |
| R-13 不用 toISOString | 东八区凌晨日期差一天 |
| R-16 前端重做后端派生动作 | 口径改成扣毛利后前端照旧算 |
| R-17 新指标三处同步 | 表头多一列 / 数值全 undefined |
| R-18 单串多文案无法断言 | 删掉第 2 条免责文案，断言照样绿 |
| R-19 build 通过≠生效 | scoped 选择器不跨组件，build 零错误 |

### 3.3 明确划出范围外

`00-主提示词.md` 第七节明确写了**四件提示词保证不了的事**：

1. UI 视觉打磨（取决于审美，需人工多轮迭代）；
2. 业务口径的业务正确性（只保证「口径不漂移」）；
3. 年度节假日表维护；
4. 大规模数据性能（需重新设计）。

**给 agent 不切实际的承诺，比少写一个功能更糟。**

### 3.4 业务细节做了隔离

主提示词第三节用一张表明确区分：

- **工程契约**（分层、口径纪律、扩展点、验证方式）→ 必须照做；
- **业务细节**（指标名、店铺概念、Excel 列名）→ 视为示例，按实际数据替换。

并给出「判断标准」：比率算法是业务口径，
「比率必须先求和再相除」是工程契约。

**这是让提示词有泛化能力的关键**——否则产出物会绑死电商场景。

## 四、验证闭环（这是本包的重点）

`03-验收清单.md` 的核心命题：

| 级别 | 说法 | 算数吗 |
| --- | --- | --- |
| ❌ | 「代码写完了」 | 不算 |
| ❌ | 「能跑了」 | 不算 |
| ❌ | 「grep 到新字符串了」 | **不算**——只能证明构建通过 |
| ✅ | 「有一条断言，它现在失败、改对了才通过」 | 算 |
| ✅ | 「浏览器里读到了计算样式」 | 算 |
| ✅ | 「另一台机器上按文档跑通了」 | 算 |

其中**真实浏览器实测**的部分尤其重要——记录了六个必知的坑：

1. headless 默认视口小（会因换行得到荒谬尺寸）；
2. 测动画要抓过程值（不是终态）；
3. 测 hover 要用真实鼠标事件；
4. 测 hover 要挑未激活样本；
5. 截图传 `clip` 可能返回空；
6. Vue 的 `:key` 不是 DOM 属性。

以本项目实测又踩了六个：点击前不 `scrollIntoView` → 事件静默丢弃；
选择器选中表头而非数据行；只改 CSS 媒体查询模拟不了 reduce；
flex item 被长文案撑开至 `min-width` 失效；子进程会主动重启；截图传 `clip` 可能返回空。

以及一个关键分类：
**「看起来没变化」要先区分「真没生效」和「生效了但幅度不可见」**——
把后者当前者重调，是浪费时间的经典错误。

## 五、维护

这套文档不是一次性产物。改动项目时**同步更新对应条目**：

| 项目里发生了什么 | 更新哪里 |
| --- | --- |
| 新踩了一个坑 | `02-口径铁律.md` 加条目（含真实数字）→ `05-反例清单.md` 加正反对照 |
| 加了新指标 / 新数据源 | `01-架构契约.md` 的扩展点矩阵 |
| 加了环境变量 | `04-迁移手册.md` 的变量表 |
| 新增了一种 UI 失效模式 | `03-验收清单.md` 的必测项 |
| 架构变了 | `01-架构契约.md` + `00-主提示词.md` 阶段划分 |

⚠️ **文档会漂移**（本包整理时就发现原项目部署指南里
「某目录默认提交」的说法早已被 `.gitignore` 排除）。
**关键事实用命令核实，不凭记忆写。**

## 六、来源

从 `JDDataDisplay`（京东 POP 商品数据可视化平台）逆向提炼。
该项目约 12300 行代码 / 35 个源文件，实际迭代中沉淀了 40+ 条「为什么不能那样写」的经验。

提炼方式：**从代码与踩坑史挖隐式契约，而非照抄文档**——
因为文档会过时，代码和教训不会。
